# RAGFlow：能力、本地部署与企业落地边界

## 结论与核验范围

**可以本地化、私有化部署，也能接本地模型；但“系统部署在内网”不自动等于“数据不出内网”。** 官方给出 Docker 自托管方案，支持 CPU 运行 DeepDoc，并支持 Ollama、Xinference、vLLM 等本地模型服务。[1][2]

它不是网盘，也不是一个大模型，而是以复杂文档解析和知识检索为基础的 RAG/Agent 平台。通过 UI、API 和工具接口，将企业资料加工成大模型能够检索、引用和使用的知识。[6][8][9]

本轮只读检查官方文档、最新 release API 和固定版本 Compose，未安装或运行 RAGFlow，未修改现有服务。2026-09-21 核到最新正式版为 **v0.27.2**，发布时间 `2026-09-10T11:11:35Z`。部署文件取自该 tag，而非 nightly/main；在线文档可能继续演进。[3]

## 一、它具体解决什么问题

### 文档解析：不只把所有字拼起来

官方提供 DeepDoc、不同分块模板及多种格式支持，包括 PDF、Word、Excel、图片、PPT。可以查看解析分块、人工修改内容、添加关键词或问题，并在检索测试页面验证召回效果。[1][6]

其价值是让操作者定位失败在哪一层：原文件是否读错、分块是否把条件切断、检索是否没找到，还是模型看到证据后答错。它不能保证任意扫描件、跨页表格或复杂图纸都被准确理解；这必须用真实资料检验。

### 检索：语义和关键词共同参与

RAGFlow 提供多路召回、融合重排与引用追溯，并非单纯将资料向量化后按距离取几段文字。[6]

工程含义：产品型号、合同编号和专有名词需要关键词匹配；同义表达需要语义匹配；Rerank 再判断哪些候选更相关。是否启用以及选什么模型，会影响费用、速度和效果。

### 回答：基于资料组织证据

可配置一个聊天助手绑定一个或多个 Dataset，并指定聊天模型。官方快速开始说明可以设置未命中时的固定回复，避免没找到资料时任意发挥。[1]

有引用不是“零幻觉证明”。验收应看引用段落是否真的支持结论，是否遗漏版本、生效日期、例外条件；不能只看答案中有几个来源标号。

### Agent、知识编译和 Wiki

当前 release 已包含 Agentic RAG 框架更新；官方知识编译文档描述 Parser → Chunker → Compiler → Indexer 管道，可生成 Wiki、Graph、Mind map、Timeline 等知识产物。[3][7]

**更正此前过度简化的对比：Wiki 并不是 WeKnora 独有。** RAGFlow 也在做知识编译与 Wiki；两者都在从问答引擎向知识与 Agent 平台扩展。当前文档注明：修改编译模板不会自动重编已完成文档，需要重新解析或运行管道；Wiki 作为知识库级产物还需触发生成，不能理解成安装后就全自动持续维护。[7]

## 二、工作链路

```text
资料摄取
  → 解析/OCR/版面处理
  → 分块与元数据
  → Embedding + 关键词索引
  → Dataset

用户问题
  → 检索与重排
  → 证据片段
  → LLM 组织答案
  → 引用与原文核对
```

这是主链路概括，不代表每种文件、每种配置都会调用所有阶段。[1][6]

需要分清三个角色：
- **Embedding 模型**：把文本映射为可做语义检索的向量。
- **Rerank 模型**：重新评估问题和候选片段的相关性。
- **Chat 模型**：根据证据组织回答或进行 Agent 推理。

RAGFlow 管组织、调度、索引和界面，模型能力需要另外提供；官方本地模型文档覆盖聊天、Embedding 和本地 Rerank 配置。[2]

## 三、本地部署的三个等级

### A. 本地系统 + 云模型

文件、索引和 Web 系统放在本地；聊天或 Embedding 调用外部 API。

- 优点：对本地算力要求较低，容易先验证检索质量。
- 代价：发送给云端的片段、问题、附件或全文受具体处理链路影响；云 Embedding 入库时可能处理所有文档分块，不只是提问阶段的少量证据。
- 适合：脱敏试验、允许外部模型处理的非敏感资料。
- **不能对客户宣称严格不出内网。**

### B. 本地系统 + 内网模型服务

文档处理、Embedding、Rerank、Chat，以及启用的视觉/OCR、语音服务全部配置为内网服务。RAGFlow 与 GPU 模型服务可以部署在不同服务器，通过内网通信。[2]

- 优点：数据路径可由企业控制，模型与知识系统可独立扩容。
- 代价：需要维护模型服务、GPU资源、版本、监控、备份和安全边界。
- 建议：面向敏感客户资料时，优先考虑此形态，不要求把所有组件塞在一台电脑上。

### C. 无互联网/隔离网部署

在 B 的基础上预先准备镜像、模型权重、OCR/解析资源和依赖；禁用联网搜索与外部工具，逐项排查外部模型、数据源、日志追踪和首次下载路径，并在禁止出网的环境验收。

这是可设计的部署目标，**不是本轮已验证的 air-gap 认证**。仅成功启动容器或打开首页不足以证明离线可用。应实际执行新文档入库、OCR、Embedding、检索和生成，再核出站网络记录。

## 四、硬件门槛

官方 Quickstart 当前列出：[1]

- x86 CPU 至少 4 核。
- RAM 至少 16 GB。
- 磁盘至少 50 GB。
- Docker 至少 24.0.0，Docker Compose 至少 v2.26.1。
- 还列出 Python 至少 3.13；容器运行时与宿主机开发工具链应按所选部署方式区分，不为看文档就升级生产宿主 Python。
- 使用代码执行沙箱才需要 gVisor；普通知识问答不应为了“功能齐全”默认开启代码执行。
- 官方预构建镜像主要支持 x86；ARM64 有测试但没有官方维护的 ARM Docker 镜像，需要自行构建。

**GPU 不是启动 RAGFlow 的硬性条件。** CPU 配置可运行 DeepDoc；聊天模型可指向别处。但这不证明 CPU 上大批量 OCR 或本地大模型生成能达到可接受的延迟。[1][2]

建议的试验起点（工程预算，不是官方承诺或实测结果）：
- 独立 Linux x86 测试机，8 核、32 GB RAM、100 GB 以上 SSD，聊天模型接现有获授权服务；给文档解析和索引留余量。
- 本地推理的显存不能给统一数字：取决于模型大小、量化、上下文长度、并发以及 Embedding/Rerank 是否共用显卡。
- 50 GB 是官方起步门槛，不是资料容量。原文件、解析中间产物、索引、模型、镜像、日志、备份都占空间。
- 本轮未体检当前服务器，不依据历史机器配置判断能否直接部署。

## 五、实际要运行哪些组件

固定 v0.27.2 配置默认使用 Elasticsearch 文档引擎、MySQL 元数据和 CPU 模式；Compose 中还包含对象存储及 Redis 兼容服务。[4][9][10]

典型职责如下：
- **RAGFlow 应用/任务执行**：Web、API、解析与问答流程。
- **Elasticsearch 等文档引擎**：全文及向量检索；替代后端按版本与需求选择，不是同时全部启动。
- **MySQL 等元数据库**：用户、Dataset、配置及业务状态。
- **S3 兼容对象存储**：文件与相关产物。该版本 Compose 的 `minio` 服务实际镜像是 `pgsty/silo`，不要只按服务名推断实现。
- **Redis 兼容服务**：该版本实际使用 Valkey。
- **模型服务**：由本地/内网或外部 API 提供，不因部署 RAGFlow 自动获得足够的推理算力。

Go 相关 NATS、TEI、Jaeger、代码沙箱等按 profile/需求启用，不是基础安装都必须开启。[4]

这解释了为什么它不像一个轻量网盘插件：它是一套有状态的知识处理系统。

## 六、生产上线容易忽略的边界

1. **默认部署文件不是安全生产模板。** 官方 `.env` 明确要求修改默认密码；Compose 映射了多个业务与基础设施端口，应缩小到回环或内网，仅通过受控 HTTPS 入口访问，不把数据库和管理面直接暴露公网。[4][9][10]
2. **数据源连接不等于原权限继承。** 即使能同步 SharePoint/OneDrive，也不能据此承诺按源文件 ACL 自动裁剪答案。本轮未完成源权限到 Dataset/检索权限的映射审查；敏感部门资料应分隔，并做跨用户越权测试。
3. **Embedding 空间不可混用。** 官方要求同一 Dataset 使用一致的 Embedding 模型，解析后不能随意更换。换模型应按新索引重建与迁移计划处理，不仅看维度相同。[1]
4. **备份必须成套。** 原文件、元数据、检索索引、配置及密钥需要一致性恢复方案；只备份上传目录无法证明可恢复。不要使用会删除 volumes 的清理命令来“修复启动”。
5. **沙箱扩大攻击面。** 当前示例 sandbox manager 为 privileged 且挂载 Docker socket；即使执行容器有隔离，也应单独评估管理面与主机权限，初期不启用。[4]
6. **版本与费用。** 固定发布 tag，升级前验证数据迁移和回滚；知识编译、文档增强、Agent 多轮检索会增加调用成本，不因开源而消失。[3][7]
7. **许可。** RAGFlow 主项目为 Apache-2.0，可作为商业交付候选；模型权重、第三方镜像和其他依赖仍需分别审查许可与分发义务。[5]

## 七、与 Hermes、M365 怎样组合

### 推荐试验方式：让 RAGFlow 提供知识，不重复包办一切

```text
群聊/业务入口
  → Hermes：理解任务、权限判断、组织执行
  → RAGFlow：检索指定资料并返回原文证据
  → Hermes：综合回答/生成交付物
```

官方提供 HTTP API 和 MCP 配置入口，因此存在接口集成路径；本轮没有实测 Hermes 或 M365 联调。[8][9]

设计上优先让 Hermes 获取原始证据，而不是每次调用 RAGFlow 生成答案、再由 Hermes 二次总结。后者可能重复消耗模型、降低出处清晰度；具体选择需看 API 返回内容与效果。

如果客户已经在 M365 中完成文档协作与权限管理，先验证现有 SharePoint + Copilot 能否满足需求。RAGFlow 更适合需要私有模型、多源文档、可调解析检索和可嵌入应用的项目；不替代 Office 在线协作、文件同步及源系统权限治理。

## 八、最小验收清单

建议测试集而非性能承诺：
- 选择脱敏资料，覆盖文本 PDF、扫描件、复杂表格、Word 和过期版本。
- 准备带原文依据的问题，包含明确答案、跨文档问题、资料缺失问题和权限隔离问题。
- 分别测：解析是否完整、检索是否命中、引用是否支持答案、拒答是否合理。
- 修改/删除源资料后，确认索引与回答同步变化；测试相似但相互矛盾的版本。
- 多人并发与大文件入库同时进行，记录实际延迟、失败、CPU/RAM及模型用量。
- 做一次备份恢复；严格内网方案再做断网及出站流量验收。

**推荐顺序：先用少量脱敏资料证明“找得准、引得对”，再投入本地 GPU、知识编译或复杂 Agent。**
