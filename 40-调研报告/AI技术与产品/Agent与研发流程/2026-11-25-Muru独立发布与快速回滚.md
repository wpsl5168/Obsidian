# 更新网站时，怎样保留一条能立即退回的路？

原文：Muru: releases, not restarts
作者：Graham Dumpleton｜个人技术博客｜2026-11-12。[1]

Python 网站更新代码时，新版可能启动不了，也可能上线后才出错。[1]作者用一个从 SQLite 数据库读取订单数的小商店，演示网站托管工具 Muru 怎样让新旧版本并存、切换请求，以及这种做法仍然解决不了什么。[1]

## 1. 先把新旧版本真正分开

作者指出，gunicorn 已能通过信号启动新进程、平滑退出旧进程，但保留独立旧版本以便随时切回，通常还要自己搭配负载均衡和部署脚本；Muru 把这些步骤纳入每次发布。[1]

示例中，每版代码有独立目录；目录里有依赖锁文件 `uv.lock`、没有现成虚拟环境时，Muru 按锁文件为该版创建独立的依赖环境，并加入自己的运行库。[1]这样，为新版安装一个包，不会改变旧版正在使用的依赖。[1]

## 2. 新版启动失败，旧版继续接请求

商店初版建表后正常返回订单数；第二版改用 `markdown` 包生成页面，却忘记把它加入依赖，结果启动失败，旧版仍正常服务，失败版也没有留下运行进程。[1]

第三版补齐依赖后，Muru 等它负责处理请求的两个工作进程都就绪，才把新请求转过去；旧版先处理完已经接到的请求。[1]作者用每隔10毫秒请求一次页面的脚本观察切换，695次请求全部返回表示成功的 HTTP 200——这是该小应用的演示结果，不是所有负载下的保证。[1]

## 3. 不立刻关掉旧版，才能快速退回

切换后，旧版保留已加载应用的宿主进程，每组工作进程缩到一个，继续运行30分钟。[1]快速回滚因此依赖旧版仍在运行，而不只是磁盘上留有代码。[1]

保留期内，回滚只需让入口把请求转回旧版，无需重新构建或加载应用；这次命令耗时约五分之一秒，观察到的363次请求全部成功，旧版随后恢复到两个工作进程。[1]

被切走的新版转为备用，再执行回滚又能切过去。[1]超过30分钟、旧版已经停止时仍可回滚，但须先重新启动并等它就绪：示例约一秒，更大的应用要看加载时间。[1]

## 4. 管理进程重启，不必连业务一起停

Muru 的后台管理进程不在请求经过的路径上。[1]作者停止它时，入口和应用进程继续服务；再次启动后，管理进程找到并重新接管它们，期间脚本记录的703次请求全部成功。[1]

作者另说明，升级可重启管理进程并替换入口而不拒绝连接；已经运行的应用仍用启动时的 Muru 运行库，直到下次部署才更换。[1]这与前面的停止、恢复演示是两件事。[1]

## 5. 代码能退回，数据库却不会跟着退回

新旧版本共用数据库，因此新结构必须同时兼容正在服务和保留待回滚的旧代码。[1]作者给出的顺序是：先增加旧代码不受影响的表或带默认值的列，再上线使用它的代码；等不再有服务中或保留中的版本依赖旧结构，才删除旧字段。[1]

例子中，新版增加默认值为1的 `quantity` 列来统计商品件数，旧版继续只数订单。[1]作者实际来回切换验证两版都能工作；回滚本身不修改数据库结构。[1]

## 6. 先暂不上线，完成迁移再切流量

第四版如果直接部署，会因为能启动而获准接流量，却因数据库尚无新列而让每次请求失败。[1]作者用 `--hold` 启动它但不接普通流量，再通过 `Muru-Preview` 请求头指定访问新版，得到500错误，日志明确指出缺列；普通用户仍访问旧版。[1]

随后指定新版运行迁移，确保使用该版的脚本、Python 解释器、环境变量和密钥；`exclusive` 设置拒绝同一应用该命令的重叠执行，退出状态则让部署脚本能在迁移失败时停止。[1]

迁移成功、确认新旧页面正常后，再切换全部流量；原服务版留下备用，更早的旧版停止。[1]

## 7. 能启动，不等于业务正确

作者最后强调，这套发布流程能挡住“启动不了”，挡不住“启动正常，但某些页面有错”。[1]他把小流量试运行、根据实际请求表现与旧版比较后再扩大流量，留到下一篇讨论；本文没有展示这一步的结果。[1]

补充：独立版本仍可继承上次未被本次设置覆盖的配置，环境变量按名字继承；`--dry-run` 只展示计划及配置来源，`--fresh` 则不继承上版设置。[1]
