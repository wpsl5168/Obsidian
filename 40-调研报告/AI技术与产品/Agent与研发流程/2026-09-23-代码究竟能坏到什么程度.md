# 代码究竟能坏到什么程度？

原文：There's No Limit to How Bad Code Can Get
作者：Zach Kehs｜个人博客｜2026-09-04。[1]

文章从作者在 Amazon 维护订单系统的经历出发，讨论为什么“沉船”和“技术债”这些比喻，会让人误以为糟糕代码迟早会触底，或能靠一次重写清零。[1]

## 1. 系统能运转，不代表它仍然容易维护

作者回忆，订单处理表面上只是写数据库、调用其他团队的服务；他和同事估计，合理实现只需不超过24名优秀工程师维护演进，实际组织却有数百人，已无人容易掌握全貌。[1] 人员流动带走业务知识，文档过时或缺失，跨团队追踪代码困难，让人不敢碰那些没人理解的部分。[1] 故障告警能推动补救，使系统继续运行，却没有消除修改困难和性能问题，新功能仍不断叠上去。[1]

他特意说明，这段回忆省略了很多细节，只用于说明问题，不是在追究个人或团队责任。[1]

## 2. 改造计划也可能继续增加复杂度

在他描述的组织里，新经理或资深工程师提出架构改造，管理层表示支持，但现有工程师没有余力，于是继续招人、增加团队。[1] 理解系统需要数年，系统又不断变化，而组织和个人晋升都等不了那么久，改造只能在信息不完整时启动。[1]

结果往往是新架构的一部分永久接到旧系统上，负责人晋升后离开，迁移因痛苦且不受欢迎而没有完成，新增人员也留下来。[1] 作者承认，自己若留下，也可能走同样的晋升路径，未必做得更好。[1]

## 3. 公司可能撑不住，代码却未必会“触底”

作者区分了企业生存与代码质量：现金流充裕的企业可能承受局部低效，业务更依赖软件质量的公司则可能因此给竞争者留下机会。[1]

软件当然可能完全失效，但导致停摆的改动通常会被迅速回滚，此前让代码更难维护的许多改动却留了下来。[1] 在他的论述中，代码可以继续增加间接层、继续变慢；维护成本超过收益，或几乎每次发布都会出故障时，先承受不住的是业务，而非代码抵达了某个天然下限。[1]

## 4. 技术债很少有“破产清零”的出口

债务能不断累积，因此比“沉船”更贴近作者描述的问题，但现实债务有破产程序，软件对应的彻底重写却很少是可行选项。[1] 他认为，相信“以后重写就能解决”，容易让今天继续拖延治理显得无害；软件质量不会自动跨过某个阈值，迫使组织开始认真维护。[1]

## 5. 另起新系统，也不等于摆脱旧系统

作者把一种做法称为 side-channel：分出团队，针对新用途建立完全独立、只含最低必要功能的系统，之后再让它承接更多新用途。[1] 但旧业务仍然存在，旧系统必须继续维护，组织还要反复决定后续需求交给哪一套系统。[1]

他在脚注中强调，这不同于通过代理层逐步替换旧系统的 strangler fig 模式；这里的新系统刻意不依赖旧系统协作，没有那层代理，也没有完成替换的保证。[1]

## 6. 大模型不会自行修正组织激励

文章只在脚注中简短讨论 LLM：作者的看法是，如果质量退化源于公司的激励与文化，大模型不会改变这些原因，只会沿既有方向加速。[1] 这是他对前述组织问题的延伸判断，文章没有把它作为经过实验验证的结论展开。[1]
