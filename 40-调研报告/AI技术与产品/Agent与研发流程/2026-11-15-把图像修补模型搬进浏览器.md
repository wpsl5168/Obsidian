# 把原本依赖 NVIDIA 的图像修补模型，搬进浏览器

Simon Willison｜2026年6月22日
原文：Porting the Moebius 0.2B image inpainting model to run in the browser with Claude Code。[1]

Moebius 可以让用户圈出图片中要移除的区域，再生成内容填补空缺。[1]Simon 用 Claude Code 把它移植成网页：打开图片、圈选、点击修补即可，非正方形图片会先补边。[1]

## 1. 从一个小模型开始，试试能否摆脱原有运行环境

当时发布的模型依赖 PyTorch 机器学习框架和 NVIDIA CUDA 计算环境。[1]看到它标示为 0.2B（约2亿参数），Simon 想尝试让浏览器通过 WebGPU 调用图形处理能力来运行它。[1]

这是他开发 Datasette 期间的支线项目：Codex 处理中等规模改动时，他常要等5–10分钟，便另开 Claude Code 做移植；这个时间不是移植总工时。[1]

## 2. 先查代码和权重，再把研究结果交给编程 Agent

他先让普通 Claude 查看仓库，确认代码、模型权重和现有运行方式，再讨论浏览器移植的可行性。[1]Claude 建议跳过他最初想到的 Transformers.js，直接使用更底层的 ONNX Runtime Web，通过 WebGPU 执行模型。[1]

这里的 ONNX 是保存模型计算流程和已学参数的通用格式，描述“计算什么”，不限定具体硬件；PyTorch 本身提供导出功能。[1]Simon 将研究结论存成 research.md，并提前下载源码、权重和相关库，让 Claude Code 接着实现。[1]

## 3. 人不写代码，但持续试用、报错和纠偏

他要求 Agent 先写计划、边做边更新，另存发现问题的笔记，并频繁提交版本，方便自己和后续会话接手。[1]出现可运行版本后，他在 Chrome 中实际操作，把错误文字和截图贴回去，经过几轮修正才得到初步可用的工具。[1]

## 4. 模型文件和网页分开发布，还要处理部署地址

Simon 手动创建 Hugging Face 模型仓库，提供能写入该仓库的访问令牌，Claude Code 才得以上传转换后的1.24GB ONNX 权重。[1]网页代码则放到 GitHub Pages，不把大模型文件一起塞进代码仓库。[1]

他明确告诉 Agent 最终访问地址，便于它调整资源路径，避免本地能跑、上线却找不到文件。[1]

## 5. 能运行之后，又碰到反复下载的问题

上线后，每次刷新似乎都会重新下载约1.3GB权重。[1]Simon 怀疑与 Hugging Face 的重定向有关，但文章没有确认这个原因。[1]

他提供了已有的 Whisper Web 示例，让子 Agent 研究它怎样缓存；使用子 Agent，是为了避免分析混淆后的 JavaScript 耗尽主会话上下文。[1]Claude 找到 CacheStorage——浏览器保存、复用下载资源的接口——并把它加进项目，解决缓存需求；首次的大文件下载仍然存在。[1]

## 6. 做成了工具，不等于掌握了背后的技术

Simon 报告，Claude Opus 4.8 完成了模型转换、发布和网页开发，他也在 Chrome、Firefox、Safari 中试过成品。[1]这是文章当时的个人实践，并非对所有设备的兼容性保证；文中没有给出运行速度或修补质量的系统评测。[1]纯浏览器端修补得以实现，前提是用户能接受约1.3GB的模型下载。[1]

他同时坦言，自己没读项目中的任何一行代码，参与的是测试、提出小功能改进和提供参考案例，因此对 WebGPU、ONNX 和模型本身所学有限。[1]之后他再让 Claude 阅读完成的仓库，讲解实现过程，并将生成的教学材料保存为 understanding.md。[1]

补充：项目采用 ONNX 的 opset 18，固定可用计算操作及其含义；这属于该项目的实现选择。[1]
