# 让 Agent 实际试用自己写出的代码

作者：Simon Willison｜《Agentic Engineering Patterns》章节：Agentic manual testing

这篇文章讨论：除了编写和运行自动化测试，怎样让 coding agent 实际调用接口、操作网页，并留下可查看的测试记录。[1]

## 1. 测试全绿，功能仍可能不能用

作者强调，coding agent 的重要能力是执行自己写出的代码，再根据结果继续修改；代码尚未运行，不能先认定它能用。[1]

单元测试和测试先行的 TDD 很有价值，但也可能出现测试全部通过、服务器启动却崩溃，或页面缺少重要元素的情况。[1] 他因此保留发布前亲眼查看功能的习惯，也让 Agent 做探索性试用，寻找既有测试没有覆盖的问题。[1]

## 2. 根据代码类型选择试用方式

对于 Python 库，可以让 Agent 用 `python -c` 直接调用新函数，尝试边界情况；其他语言则可以写一个小型演示程序，编译后运行。[1] 作者有时指定把临时程序放进 `/tmp`，避免误提交到代码仓库。[1]

对于 JSON API，他会要求“启动开发服务器，用 `curl` 探索新接口”。[1] 按他的经验，“探索”这个措辞常会促使 Agent 尝试接口的不同方面，而不只执行一次固定调用。[1]

## 3. 网页需要在真实浏览器里检查

文章介绍了几种方式：Playwright 提供浏览器自动化接口；Vercel 的 agent-browser 将它包装成面向 Agent 的 CLI；作者自己的 Rodney 则通过 Chrome DevTools Protocol 控制 Chrome。[1]

他的提示词会要求启动开发服务器，运行 `uvx rodney --help`，再测试新首页、查看截图，确认菜单位置。[1] 这里的安排各有用途：`uvx` 首次调用时安装工具，帮助文本让 Agent 了解用法，“查看截图”则提醒它用视觉能力检查页面外观。[1] 这些工具还可以点击、输入、滚动、运行 JavaScript，或读取页面的无障碍树。[1]

## 4. 把探索发现的问题留在自动化测试里

Agent 试出问题后，作者会要求用 red/green TDD 修复，让这个案例进入长期保留的自动化测试；浏览器试用发现的问题也一样。[1]

他同时指出，浏览器测试过去常因不稳定而令人却步，HTML 的小改动就可能让一批测试失败。[1] 他的经验判断是，让 coding agent 随界面变化维护这些测试，可以明显减轻持续维护的负担。[1]

## 5. 测试记录要包含实际执行结果

作者开发 Showboat，是为了让 Agent 把试用过程整理成文档，展示做过什么、如何确认效果。[1] 其中 `note` 添加 Markdown 说明，`exec` 记录命令、执行命令并保存输出，`image` 插入截图等图片。[1]

他尤其看重 `exec`：文档里的结果来自命令执行，而非让 Agent 自己描述“应该发生了什么”。[1] 这个设计旨在减少把期望结果冒充实际结果的行为，让读者能看到 Agent 做了什么，以及实际得到了什么。[1]
