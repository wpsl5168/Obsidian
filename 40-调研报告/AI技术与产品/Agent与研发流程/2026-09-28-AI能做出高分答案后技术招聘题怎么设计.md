# AI 能做出高分答案后，技术招聘题怎么设计？

Tristan Hume｜Anthropic Engineering｜2026年1月21日。[1]
原题：Designing AI-resistant technical evaluations

Anthropic 的性能工程招聘题允许使用 AI，但模型升级后，原先能区分候选人水平的题目逐渐失效。[1] 负责设计题目的 Hume 记录了三版测试的调整，以及保留区分度所付出的代价。[1]

- **最初的目标，是让候选人有时间理解系统、展示优化能力。**
第一版给出4小时，候选人在自己的编辑器里，把模拟加速器上的串行树遍历逐步改成并行实现，涉及多核、SIMD 向量化和 VLIW 指令打包；题目刻意不要求深度学习经验，并留出调试、造工具和继续深挖的空间。[1] 文中称，测试已有超过1000人完成，帮助团队招聘了数十名工程师，也识别出多位履历不长、实际表现很强的本科毕业生。[1]

- **第二版从模型开始吃力的地方起步。**
到2025年5月，作者测试的预发布 Opus 4 已能在4小时内超过几乎所有人类提交，于是把它开始遇到困难的位置设为新起点，清理初始代码、增加机器特性，移除已无法提供区分度的多核部分。[1] 时限也从4小时缩到2小时，主要为了减少招聘排期拖延；考查重心转向优化思路，降低调试和代码量的比重。[1]

- **Opus 4.5 再次追上，但过程包含人的提示。**
作者观察到，它不到一小时就达到通过线，随后误以为碰到了无法突破的内存带宽瓶颈；得到“可以达到多少周期”的提示后，它找到了利用问题结构绕过瓶颈的方法，最终在2小时内追平同限时最佳人类成绩，而那位候选人也大量使用了 Claude 4。[1] 团队随后用内部测试运行框架复测，报告模型能在2小时内超过人类成绩，继续投入计算还可改善结果。[1]

- **禁用 AI 或直接提高分数线，都有问题。**
Hume 不愿禁用 AI，既因为难以执行，也因为实际工作本就会使用它；他也担心，单纯要求“显著超过 Claude Code”，会让候选人在理解题目时已落后于模型，最后只剩旁观。[1] 文中说，团队工作正更多涉及复杂调试、系统设计、正确性验证和简化模型代码，但这些能力很难在缺乏共同背景的短时测试中客观衡量。[1]

- **换成自己觉得难的题，也未必挡得住模型。**
他尝试把真实工作中的数据转置与存储体冲突优化改成新题；Opus 4.5 先通过改写整个计算过程绕开数据转置，作者封住这条实际场景不可用的路径后，它又在更长思考预算下解出了问题。[1] Hume 回顾认为，这类难题已有跨平台经验可供模型借鉴，自己曾需从基本原理推导，并不意味着模型也得如此。[1]

- **第三版改用陌生指令集，同时考查是否值得造工具。**
受 Zachtronics 编程解谜游戏启发，新测试让候选人在极小、严格受限的指令集中，把解法压缩到尽可能少的指令；作者测试的中高难度题挡住了 Opus 4.5，同事也能做得比模型好。[1] 初始代码只验证答案，不提供可视化或调试器：候选人可以精心插入打印语句，也可让 AI 生成交互式调试器，如何投入工具建设同样是考查内容。[1]

- **新区分度换来了真实性损失，效果仍属早期观察。**
作者称，新题成绩与候选人过往工作的质量较为吻合，多个独立子题也可能降低成绩波动，但他遗憾地放弃了原题贴近实际工作、可多方向深入的特点。[1] 文末开放了旧题的变体，保留“不限时最佳人类仍领先”的限定；列出的1790、1579周期分别对应 Opus 4.5 的普通 Claude Code 会话和内部框架下2小时运行，属于模拟机器周期数，不是耗时秒数。[1]
