# 写代码变便宜后，软件开发者还做什么？

原文：We are all Product Engineers now
作者：Laurie Voss｜Seldo.com｜2026-09-14。[1]

这篇文章讨论：如果生成代码越来越便宜，开发者的工作会转向哪里？作者给出的是有条件的十年预测，不是宣告软件研发已经能全程自动化。[1]

## 1. 先接受两个假设，后面的预测才成立

作者认为写代码的成本已经大幅下降，并假设 Agent 最终也能做好审查、测试、修复、部署和运维；但他承认，写作当时模型在这些后续环节还不够好。[1]

另一前提是：未来十年，软件需求实际上没有上限。[1]牙医、学校等机构的软件不好用，许多小企业还靠表格、群聊和某个员工的记忆运转；他据此推测，价格下降会释放大量未满足的需求，而非让开发者整体变得多余。[1]

## 2. 最先受冲击的，是“拿到明确任务后写代码”的入门岗位

过去，初级工程师按工单写代码，资深工程师审查，新人逐渐积累判断力。[1]作者认为 Agent 首先替代的恰好是这一级台阶，因此问题不只是少招新人，还有未来资深人才从哪里来。[1]

文中转引的研究称：在容易受 AI 影响的岗位中，22—25岁人群的就业水平，比“如果跟随较低暴露同龄群体的轨迹发展”的基线低19%；主要表现为减少招聘，而非裁员。[1]这不是所有程序员就业同比下降19%。[1]

另一份报告显示，入门招聘减少的同时，工程师占招聘的比重却从46%升至55%。[1]作者据此区分“还需要工程师”和“还需要主要负责照说明写代码的人”。[1]

## 3. 后续环节有进展，但生成得快不等于交付可靠

作者引用一项覆盖157个开源项目、567个 Claude Code 代码修改请求的研究：84%最终被合并，人类对照为91%；略多于一半无需人类修改就被合并。[1]“无人修改”不等于无人审查，合并率也不能直接当作软件无缺陷率。[1]

审查能力跟不上生成量，已造成负担。[1]文中另一项研究分析了约3.3万个 Agent 修改请求，指出很多请求没有记录在案的审查；在获得审查的 Agent 请求中，58%只有另一个 Agent 担任审查者。[1]

至于部署、运维和扩容，作者明确说数据很少，主要依赖“这些环节也会自动化”的开篇假设，不能当成已经发生的事实。[1]

## 4. 留下来的工作，是弄清具体的人到底要什么

客户说“我要管理订单”，面包店与汽车零件厂要的可能完全不同，甚至两家面包店也不一样。[1]作者认为，这些尚未表达的需求不在现成训练数据里，需要有人询问、整理成可实施的要求，再让客户确认做出来的东西是否符合原意，第一次通常对不上。[1]

这种理解很难直接复用到另一位客户：通用软件即使提供大量配置，也未必合适。[1]因此，他预测制作成本越低，瓶颈越集中到如何准确描述问题。[1]

还要区分“功能正确”和“人愿意使用”：两个方案都能完成任务，体验仍可能差很多。[1]作者把设计单独列出，认为它需要逐产品投入；但也承认，设计能否长期不被自动化，比需求理解更不确定，他无法量化这种优势。[1]

## 5. 产品与工程的工作，可能重新合到一个人身上

文章回顾了两种需求翻译角色：系统分析员把企业需求写给程序员；软件面向消费者后，产品经理通过研究市场承担这项工作。[1]作者预期，产品与工程之间的分工会再次收拢，并称之为“产品工程”。[1]

他把前线部署工程师（FDE）视为一个早期例子：到客户现场理解业务，在客户已有系统中写生产代码，反复调整直到能用。[1]这里付费购买的不只是代码，还有把模糊问题变成具体验收要求的能力。[1]

## 6. 新工作需要判断力，但旧培养路径正在受损

作者担心，行业过去让新人通过写代码、接受审查，逐年学会理解需求和判断质量，却没有同等规模的替代训练。[1]

文中举例：Google 的助理产品经理培养项目每年约从1.2万名申请者中录取50人；加上其他公司的同类项目，作者粗估也只有每年数百人，不能把它理解为全球只有50人在受训。[1]

他提到 IBM 正把入门岗位转向客户接触和需求描述，也预期企业与学校会逐渐增加培养；但调整可能很慢，一批新人会在过渡中受损。[1]

## 7. 即便总就业增长，喜欢编程的人也可能失去想做的工作

有人喜欢的是设计简洁的代码、解开难查的 bug，并不喜欢访谈客户。[1]作者承认，职业内容变成另一种工作就是损失，而编程实践原本也是形成判断力的重要来源；他预计技艺会以爱好及少数高溢价工作的形式延续。[1]

他的最终预测是：十年动荡后，开发者更多、报酬大致相近，但工作更像产品工程，手写代码占比很小。[1]这个判断有明显边界：他本人就偏爱定义问题，承认可能高估自己擅长的工作；文章不讨论营销、获客等职能，也不对二十年后或通用智能出现后的就业作判断。[1]
