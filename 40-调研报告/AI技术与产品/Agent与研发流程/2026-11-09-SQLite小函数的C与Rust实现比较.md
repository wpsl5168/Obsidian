# 同一个 SQLite 小函数，为什么 C 起初比 Rust 慢？

Simon Willison｜2026-11-08
原文：parse_number() as a SQLite extension: C vs Rust。[1]

在 SQLite 数据库里，把“-$1,234.56”这样的文本变成能求和、排序的数字，用 C 还是 Rust 写扩展更合适？Simon 在遛狗时提出这个问题，让普通 Claude 聊天中的 Opus 5.5 比较速度、代码复杂度和编译后的文件大小，再要求它优化 C 版本并整理报告。[1]以下梳理博客及其配套报告；报告明确注明全文和代码由大模型生成，测试数字是原文报告的结果。[2]

## 1. 先统一“什么算数字”，再比较实现

四个版本采用相同规则：去掉任意位置的逗号、美元符号、英镑符号和百分号，忽略首尾空白，允许首个数字前有一个负号、最多一个小数点，至少需要一位数字；无法解析就返回空值 NULL。[2]这里“12.5%”变成 12.5，不是 0.125；科学计数法“1e5”、正号“+5”、内部空格“1 000”和欧元符号都不接受。[2]

现成的整数、实数原样返回，NULL 和二进制数据返回 NULL；文本没有小数点时优先返回整数，超出 64 位整数范围才转实数，有小数点则返回实数。[2]这些约定决定了比较的不只是算得快，还包括返回值和数据类型是否一致。[2]

## 2. C 文件更小，却在解析小数时落后

最初 C 扩展约 14 KB，两种 Rust 扩展（分别使用 rusqlite、sqlite-loadable 接口库）约 321 KB、298 KB；但混合数据上，普通 C 每行净成本为 67.3 纳秒，Rust 分别为 45.9、40.5 纳秒。[1][2]

差距集中在小数：普通 C 为 106.3 纳秒，Rust 为 54.5、46.5；纯整数反而是 C 更快。[2]报告把原因指向具体实现：C 先把清洗后的字符复制到缓冲区，再调用通用转换函数 strtod；Rust 的小数解析器已有针对常见数字的快速处理路径。[2]

## 3. 这些数字不是完整查询耗时

测试在 2 vCPU 的 Linux x86-64 虚拟机上运行，使用 SQLite 3.53.1、gcc 13.3 和 rustc 1.97。[2]扩展由 Python 加载，但对 200 万行逐行解析并求和的循环在 SQLite 内执行；各版本交替运行，取 15 次中的最快值，再扣除同一批数据执行 sum(length(v)) 的扫描基线。[2]

因此，文中的“纳秒/行”是扣除基线后的函数调用与解析成本，不是平均响应时间，也不是整个查询耗时；混合数据还包含 10% 无效内容。[2]

## 4. 人要求再优化后，C 避开了常见输入的慢路径

Simon 要求 Claude 自己写一段 C 小数解析代码，追上或超过 Rust。[1]新版本在扫描字符时直接累积数字：有效数字组成的整数不超过 2^53、小数点后不超过 22 位等条件满足时，用一次正确舍入的除法得到结果；更长或不满足条件的输入仍回退到 strtod，整数也不再写入字符缓冲区。[2]

优化后，C 在混合、整数、小数数据上的净成本分别为 19.2、15.8、17.5 纳秒/行。[2]报告指出，Rust 版本仍有接口包装或每次申请内存的成本；仅把其中一个版本改为不必每次动态申请内存的缓冲区，整数测试只从约 35 降到 31 纳秒。[2]纯 SQL 嵌套 replace 更慢，但它没有执行同样严格的解析规则，功能并不完全等价。[2]

## 5. 速度之外，还要付出代码和构建成本

普通 C、优化 C 分别为 75、104 行；Rust 两种接口代码为 36、30 行，另各需共享的 41 行解析器。[2]Rust 帮忙处理内存和整数溢出，C 则要手工照顾缓冲区、溢出、最小整数及浮点细节。[2]

C 从零编译约 0.1 秒，Rust 两版分别约 11、72 秒，依赖 20、62 个 Rust 包，后者还需要 libclang，而且 sqlite-loadable 当时仍是 alpha 版。[2]即使优先优化文件大小，Rust 成品仍约 306、284 KB；报告解释，它们带入了标准库、格式化和异常终止处理代码，C 两版则保持约 14 KB。[2]

## 6. 检查没有发现差异，但仍有适用边界

报告给出 40 个手写用例，检查数值和类型；随机检查使用 4 个种子、每个生成 50 万输入，再分别测试 4 个扩展，共 800 万次比较，未发现不一致。[2]参照是使用 Python float 的实现，逐位比较还包括负零及整数、实数类型差异；输入覆盖随机垃圾、长小数和接近 2^53 的数值。[2]

C 版本的 strtod 仍受宿主区域设置影响，优化版回退时也有这个问题；快速路径还要求特定浮点计算模式，否则会被禁用。[2]代码、测试脚本和原始输出已公开，但上述检查不能消除这些平台限制。[2]
