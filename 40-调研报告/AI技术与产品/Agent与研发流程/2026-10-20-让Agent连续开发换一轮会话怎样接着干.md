# 让 Agent 连续开发：换一轮会话，怎样接着干？

原文：Effective harnesses for long-running agents
作者：Justin Young｜Anthropic｜2025-11-26。[1]

一个软件项目可能要做几小时甚至几天，但模型每轮能读入的信息有限。[1] 文章讨论的是：上一轮没做完，下一轮怎样知道做到哪儿、还有什么没做，而不是重新摸索或误报完工。[1]

## 1. 把聊天记录压短，仍可能丢掉交接信息

上下文压缩会把先前记录缩短，为后续工作腾位置，但不保证交接清楚。[1] 在文中的 Opus 4.5 实验里，仅靠 Claude Agent SDK 提供的运行框架、循环执行和“仿做 claude.ai”这种大目标，仍不足以做出生产级网页应用。[1] 常见失败有两种：一次铺开太多功能，做到一半耗尽上下文，留下没记录的半成品；或者下一轮看到已有部分功能，就宣布整个项目完成。[1]

## 2. 第一轮准备环境，后续各轮接手开发

团队把首轮设为“初始化 Agent”：准备启动服务的 init.sh、记录工作进展的 claude-progress.txt，以及初始 Git 提交；后续“编码 Agent”负责逐步推进并留下交接材料。[1] 这里的两类 Agent 只是初始用户提示不同，系统提示、工具和运行框架相同，并不是两个不同模型。[1]

## 3. 先写清全部验收项目，防止做一点就算完成

仿 claude.ai 的案例被拆成200多项功能，每项列出操作与预期结果，最初全部标为“未通过”。[1] 例如新建聊天、输入问题、发送并看到 AI 回复，不能只凭界面已经出现就算完成。[1] 后续 Agent 被明确要求只更新通过状态，不能删改测试来掩盖缺失功能；团队选用 JSON 保存清单，是因为实验中模型比起 Markdown 更少误改或覆盖这种文件。[1]

## 4. 一次只推进一个功能，结束时留下能接手的代码

后续每轮只做一个功能，完成改动后写清 Git 提交说明和进度总结。[1] 所谓“干净状态”，是没有重大错误、代码有序且文档清楚，下一轮可以开始新功能，不必先收拾无关的烂摊子。[1] Git 历史也让 Agent 能撤回错误改动，恢复可运行版本，减少反复猜测和修复环境的时间。[1]

## 5. 测试要走完用户操作，不能只看接口成功

团队发现，模型即使跑了单元测试，或用 curl 请求开发服务器，也可能漏掉整条用户流程不可用的问题。[1] 明确要求它使用浏览器自动化、像用户一样操作后，验证效果明显改善，能发现并修复代码表面看不出的错误；功能必须认真测试后才能标为通过。[1] 这仍有盲区：文章当时使用的 Puppeteer MCP 工具无法让 Claude 看到浏览器原生 alert 弹窗，依赖这种弹窗的功能因此更容易出错。[1]

## 6. 每轮先确认旧功能没坏，再做下一项

新一轮先确认工作目录，读取 Git 历史、进度记录和功能清单，再用启动脚本运行服务、做基础端到端检查。[1] 聊天应用的检查是新建会话、发送消息并收到回复；如果已有功能坏了，先修复，再推进优先级最高的未完成功能，避免在破损状态上继续叠加改动。[1]

这套方案针对全栈网页应用演示。[1] 作者尚未确定：一个通用编码 Agent 更好，还是分出测试、质检、代码清理等专门 Agent 更好；推广到科研、金融建模也仍是未来方向，不是已经验证的结果。[1]
