# AI 写代码越来越快，版本管理先撑不住了

原文：Redesigning source control at Anthropic
作者：Nick G. 与 Anthropic 源码管理团队
发布：2026-10-13；10月15日补充技术来源说明。[1]

Anthropic 报告，2026年5月至9月，每天合并的代码改动从约2500次增至超过3万次，版本管理、构建和自动测试逐渐成为瓶颈。[1]这篇文章介绍他们为何迁出 Git，以及自建 Scion 的收益与代价。[1]

## 1. 先用过 Git 的扩展办法，仍追不上增长

其主分支历史接近100GB，压缩后的工作副本超过25GB；仅 CI，也就是持续集成的自动构建和测试，每天就取代码约2500万次。[1]作者估计，若每次朴素地拉取，每日流量会超过600PB；这是基于 CI 次数的假设估计，不是实际流量，还没计入开发环境、Agent 沙箱和研究作业。[1]

他们用过浅克隆、只取部分目录、按需获取对象、仓库快照，最多运行过数百个内部 Git 镜像。[1]但更新越快，快照越容易落后；只保留部分仓库，又增加了查询历史和代码修改者的维护难度。[1]

## 2. 客户端一直在线，就不必各自保存完整仓库

Git 支持离线查历史、比较版本和切换代码；Scion 的主要用户却是始终在线的 Agent 和自动作业。[1]因此，提交、合并、历史查询都交给服务器，客户端只留有限缓存和需要编辑的文件，代价是不能像 Git 那样独立离线工作。[1]

许多任务甚至不需要把代码取到本地：问“两次提交差在哪里”，或修改文件，都可以调用服务器接口；确实需要本地文件时，再按目录或实际读取需求获取。[1]

## 3. 只处理新增变化，让缓存承担重复读取

Scion 每次记录相对第一个父版本改了哪些文件，文件内容另存；再为历史追踪等查询生成可提前或按需计算的索引。[1]它减少对分支指针等全局状态的依赖，让提交开销随改动大小增长，而不是随整个仓库增长，服务器也不必有一台机器装下完整仓库。[1]

客户端只请求缺少且内容不变的对象，同机任务共享缓存，再逐层访问区域缓存和权威服务器。[1]层级被严格限制，防止区域缓存故障后，请求绕过它压垮上游。[1]

团队报告，各层缓存命中率超过99%；相较旧 Git 镜像基础设施，CPU、内存需求降至约1/200；CI 与研究作业取代码快了两个数量级，从分钟级变为秒级，CI 释放了25%的 CPU 容量。[1]这些是内部特定负载的结果，不是整体研发效率提升同样倍数。[1]

## 4. AI 加快了建设，人仍要否决错误设计

7人团队用5个月建成 Scion、代码审查工具 Antique 及约6个关联系统，并完成迁移。[1]一个例子是让 Claude Mythos Preview 的早期内部版本重写原先手写的导入管道：团队称，没有追加指令，新版内存用量约为原来的1/20、速度为4倍，同时保持导入顺序和数据结构等必要约束。[1]

工程师仍负责跨系统取舍：Agent 曾遍历提交日志查合并时间，而不是询问现成的审查工具；让模型专门挑错的审查，也曾导致对内部服务过度校验、徒增复杂度。[1]每次改动仍由人审查，只是重点转向改动意图，而非逐行阅读。[1]

## 5. 测试、权限和监控也一起补上

团队用 Claude 建立隔离环境中的交互模拟、随机输入测试和限流机制。[1]权限可以细到目录，审查规则能区分“只改注释”与“修改敏感逻辑”，让人集中处理后果严重的变更。[1]

运维上，他们让 Claude Tag 分别盯住单个组件的日志和运行指标，寻找细微异常；传统告警仍然保留，并未被模型取代。[1]

## 6. 合并变快后，要接受新的冲突风险

一次测试尚未结束，可能已有数百甚至数千次改动合入。[1]团队没能有效沿用给整个仓库加锁、依次放行的合并队列，转而投入合并后、部署前的自动测试。[1]

代价是并发改动可能冲突。[1]作者说 Claude 通常能比人发现问题更快地修复，但没有宣称冲突已经消失，也不是取消部署前测试。[1]

## 7. 作者明确不建议把它当通用 Git 替代品

Scion 面向极大的单一代码仓库，以及海量开发者或 Agent；Anthropic 内部能投入的 token 预算，也远超其他企业现实中愿意承担的水平。[1]采用它还要连带迁移审查、搜索和 CI，现有实现高度定制，难以直接推广。[1]

文章承认借鉴了 Google Piper、Meta Sapling，尤其是其服务端 Mononoke 的数据模型等技术。[1]作者预计类似压力会在未来6—12个月更常见，因此更希望 Git 吸收服务端接口、获取协议和部分仓库读取方面的设计，而非让各家公司都重写一套。[1]
