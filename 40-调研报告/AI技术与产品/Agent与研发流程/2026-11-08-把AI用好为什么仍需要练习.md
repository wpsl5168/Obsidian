# 把 AI 用好，为什么仍需要时间和练习？

Sean Goedecke｜《Getting good at AI takes time and practice》｜2026-10-28。[1]

模型越来越强，是否可以等它成熟后再用，届时一句话交代任务就够了？作者的回答是否定的：提示技巧会变，但补充背景、认识能力边界、识别错误等经验，仍需要长期练习。[1]

## 1. 先发现它缺什么，再告诉它为什么要做

作者见过有人只说“解决我的问题”，却不交代是什么问题；也有人询问团队聊天工具 Slack 上的事情，却没让 Agent 接通 Slack，模型只能努力猜，而且容易猜错。[1] 熟练用户会发现信息缺口，退回来补背景，还会说明任务目的，让 Agent 能在不同做法之间作取舍；而人自己也往往要想一想，才能说清为什么要做。[1]

## 2. 分清“能做”“做不好”和“引导后能做好”

按作者的使用经验，模型可以帮忙构思服务架构，却不适合替他想新产品功能；代码合并请求的说明，则属于默认写不好、适当引导后能改善的任务。[1] 这些分类并无共识，不能当成所有模型的固定能力表，也不能只凭模型自述判断能力。[1] 他观察到，新模型通常在原本擅长的任务上进步更大，在弱项上改善较少，因此辨认能力边界的经验，比某条提示口诀更耐用。[1]

## 3. 知道功能存在，不等于想得到用它

他起初自己折腾 GitHub Copilot 的 MCP 服务——供 Agent 连接外部工具的服务——经弟弟提醒，才想到可以让 Copilot 自己安装。[1] 他后来才养成习惯，让 Agent 启动本地服务、发送请求，测试修改后的不同情况和边界；写文时又刚开始安排本地早上 6 点的定时任务，查看其他时区发来的消息并作初步调查。[1] 这些都是他的个人实践，不是一次统一效果测试。[1]

## 4. 审代码，要看它有没有擅自改了目标

作者认为，AI 与人类代码的常见错误不同：他把计数“差一位”列为人更容易犯的错误，而把过度设计、为自造要求牺牲重要需求，列为 AI 常见问题；这是他的经验判断，并不表示 AI 不会写错边界。[1]

注释齐全、测试很多、语法高级，也不能证明设计合理。[1] 例如，模型可能为了无关紧要的极端情况，加入互斥锁——防止多个执行流程同时操作共享数据的机制；审核者仍需判断这份复杂度是否必要，不能因代码看起来专业就相信它。[1]

## 5. 从长篇输出里找到具体说法和证据

作者把快速阅读 AI 的冗长表达也算作一项实际技能：读得多了，才容易跳过铺陈，定位它到底提出了什么主张、拿出了什么依据，减少时间和精力消耗。[1]

## 6. 这些经验也可能过时，但不是今天就没有价值

他承认，如果工具能自动补齐背景、模型能可靠完成所有任务且不犯错，人也不再需要阅读结果，这些技能可能消失。[1] 但他推测，人机配合胜过单独使用人或机器的阶段可能持续几十年；这是预测，不是已确定的时间表。[1] 他以学习 Angular、React 为例：即使当初预计技术十年后会过时，也不代表当时不值得学。[1]

## 7. 练习协作，也不能丢掉亲手积累的专业能力

文章还列出几项经验：何时纠正或放弃一轮对话、怎样给多个 Agent 分工、何时信任或核验回答，以及怎样用小模型降低成本；跟上当下技巧和模型差异，也有短期价值。[1]

作者的结论有两面：完全回避 AI 的人，可能落后于持续练习的人；但把工作全交给 AI 同样是错误，因为专业知识会帮助人更好地使用模型，而这类知识最好靠亲手实践积累。[1]
