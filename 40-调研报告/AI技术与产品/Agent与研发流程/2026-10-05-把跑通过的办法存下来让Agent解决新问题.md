# 把跑通过的办法存下来，让 Agent 用它们解决新问题

原文：Hoard things you know how to do
作者：Simon Willison｜《Agentic Engineering Patterns》章节；页面未标明发布日期。

面对新需求，开发者得先知道哪些办法可行、怎样实现。[1]Simon 介绍了自己的习惯：把亲手跑通的代码和说明留存下来，既帮助自己判断技术能做什么，也让编程 Agent 有现成例子可以组合使用。[1]

## 1. 积累的是“做得成”的证据

例如，用 Python 处理一个 100GB 的 JSON 文件，能否不把整个文件装进内存？原文用这类问题说明：知道技术大概可行，与亲眼见过代码运行，是两种不同的把握；作者没有在这里回答这些具体问题。[1]

他的看法是，软件开发能力的一部分，就是熟悉技术的可能性、限制和实现路径；掌握的具体例子越多，越容易发现解决问题的办法。[1]

## 2. 笔记留下解释，代码留下可复用的例子

Simon 用博客和 TIL（“今天学到什么”）记录摸索过程，用 GitHub 仓库存放代码，其中不少只是验证一个想法的小程序。[1]

他也让大模型帮助扩充积累：简单工具存成单个 HTML 文件，把页面、样式和交互代码放在一起；复杂探索则放进 research 仓库，要求 Agent 交回能运行的代码，以及说明发现了什么的报告。[1]

## 3. 一个扫描 PDF 识字工具，来自两个旧例子的组合

他想在浏览器里对扫描版 PDF 做文字识别（OCR）。[1]这类 PDF 只有图片，没有现成文字可读；他此前试过的 Tesseract.js 可以从图片识字，而另一个用过的库 PDF.js 可以把 PDF 的每一页转成图片，两者的代码片段都在笔记里。[1]

他把两段示例一起交给模型，要求做成一个网页：拖入 PDF 后，把每页转成 JPEG 显示出来，再逐页识字，将结果放进各张图片下方的文本框。[1]

这里用到的方法很具体：拿两个已经跑通的环节，加上明确的连接方式，让模型组装出新工具。[1]

## 4. 首个原型合用，最终结果仍经过几轮修改

这个案例发生在 2024 年 3 月，使用的是 Claude 3 Opus，早于 Claude Code 发布；并不是当时已有编程 Agent 自动完成了整项工作。[1]

据 Simon 回忆，模型首次给出的概念验证页面就符合需求，之后又迭代几次才得到最终版本，整个过程只花了几分钟；这是他的单个项目经历，不是对所有开发任务的耗时承诺。[1]

## 5. Agent 能自己取例子，但要拿到源码

对于能联网的 Agent，他给出一个进一步的提示示例：读取已有 OCR 工具和另一个图片定位工具的源码，组合出一个新工具，让用户选择 PDF 页面，再交给 Gemini 标出页面中插图的位置。[1]

他特意要求用 curl 获取原始 HTML，因为按文中描述，Claude Code 默认的 WebFetch 会返回页面摘要，而不是原始源码；要复用实现，摘要并不够。[1]

## 6. 旧项目也可以成为新项目的参考材料

例子不必全在网页上。[1]他会给本机 Agent 指定两个项目目录，让它参照旧项目添加“模拟 HTTP 请求的测试”，即不靠真实网络服务也能测试相关代码；也会让 Agent 把公开研究仓库克隆到临时目录，从中寻找实现示例，再做新的演示页面。[1]

作者最后强调，某个有用办法一旦摸索清楚，并留下说明和可运行代码，Agent 就能在以后结构相似的项目中查找、借用这些成果；前提是那些例子确实被保存下来，而且能够访问。[1]
