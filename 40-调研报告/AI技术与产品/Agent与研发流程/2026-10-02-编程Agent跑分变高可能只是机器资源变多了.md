# 编程 Agent 跑分变高，可能只是机器资源变多了

Gian Segato｜Anthropic Engineering｜2026-02-05
原题：Quantifying infrastructure noise in agentic coding evals。[1]

编程 Agent 测试不只看最终答案，还让模型安装依赖、运行程序、测试和修改。[1]Anthropic 发现：同一个模型做同一套题，仅改变运行环境的资源限制，成功率就可能相差几个百分点。[1]

## 1. 同样的资源规格，执行方式可能不同

团队在 Google Kubernetes Engine 上运行 Terminal-Bench 2.0 时，成绩与官方榜单对不上，最高约6%的任务因运行容器出错而失败，多数与模型解题能力无关。[1]

他们把每道题的建议资源同时设为“保证提供的额度”和“不能超过的上限”，短时内存峰值也可能触发强制终止；榜单采用的另一家运行环境提供方允许暂时超配，减少这种中断。[1]因此，配置数字相同，不代表实际条件相同。[1]

## 2. 少崩溃，不一定多答对

团队固定 Claude 模型、运行框架和题目，测试六档资源条件，从严格执行建议额度的1倍，到不设上限。[1]

上限从1倍放宽到3倍，基础设施错误率由5.8%降到2.1%，但成功率变化仍处于统计噪声范围。[1]两项检验分别为 p<0.001 和 p=0.40：前者变化显著，后者未显示显著差异。[1]

原因是许多原先被中断的任务，即使不中断，模型最终也解不出来；不能把减少的崩溃数直接当成新增答对数。[1]

## 3. 再加资源，开始改变能解出的题

从3倍放宽到不限额，基础设施错误率只再下降1.6个百分点，成功率却上升近4个百分点。[1]不限额时，错误率为0.5%；成功率相对1倍配置总共提高6个百分点，p<0.01。[1]

作者解释，额外资源允许 Agent 安装更大的依赖、启动更耗资源的子进程、运行更吃内存的测试。[1]这时变化已经超出“避免意外中断”，部分原本走不通的解题办法变得可行。[1]

## 4. 有些解法还没开始写，就先把内存用完

在一项根据数据拟合变量间概率关系的任务中，部分模型先安装 pandas、networkx、scikit-learn 等数据分析工具。[1]资源宽裕时能继续；资源紧张时，安装阶段就耗尽内存，尚未写出解题代码。[1]

另一种办法是只用 Python 自带的标准库实现所需数学计算，有些模型默认就会这样做。[1]严格资源限制更有利于轻量、高效的策略，宽松配置则允许使用重型工具；作者认为两种能力都可以测，但不能隐去条件后只比较一个分数。[1]

## 5. 换一套题仍有影响，但幅度不同

团队在 SWE-bench 上另做实验：227道题，每题10次采样，把可用内存提高到基线的5倍，成绩比1倍时高1.54个百分点。[1]作者解释，这套题对资源的需求较低，所以影响较小；它与前面的实验并非相同测试条件。[1]

不同 Anthropic 模型上也观察到相同方向、不同幅度的变化。[1]其他厂商模型是否如此，文中明确说尚未严格验证。[1]

## 6. 内存之外，还有尚未量化的干扰

时间限制、集群健康、硬件、并发和网络带宽也可能影响测试。[1]团队观察到通过率随一天中的时段波动，推测与流量和故障造成的 API 延迟有关，但没有正式量化这一影响。[1]

作者建议跨时段、跨日期重复测试，减少偶然波动；这不是已经证实某个时段跑分更好的结论。[1]

## 7. 作者建议公开资源下限、上限和执行方式

理想情况是测试环境与模型推理端的硬件条件都一致，但现实中未必可行。[1]文章建议按题目分别公布保底额度和硬上限，并实测校准二者之间的余量：减少意外中断，同时使区间两端的成绩差异仍处于噪声内。[1]此次3倍上限是一个折中，不是所有评测的通用标准。[1]

文中指出，中等资源配置之间的成绩差已接近2个百分点，常规统计置信区间另有1–2个百分点的波动范围，基础设施干扰并未被后者包含。[1]因此，在配置尚未公开并对齐之前，作者建议谨慎看待低于3个百分点的榜单差距；这不等于认定小幅领先必然无效。[1]
