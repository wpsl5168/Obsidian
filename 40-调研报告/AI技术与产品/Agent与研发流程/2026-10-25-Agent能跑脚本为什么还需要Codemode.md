# Agent 已经能跑脚本，为什么还需要 Codemode？

原文：What is Codemode
作者：Armin Ronacher｜2026-10-06。[1]

作者此前主张让 Agent 多用命令行和脚本，少把大量工具定义塞进模型上下文；如今 Pi 1.0 却通过 Codemode 接入了 MCP——一种连接外部工具服务的协议，本文解释这两件事为什么不矛盾。[1]

## 1. 有些操作，光靠命令行并不顺手

命令行便于把多个程序串起来，模型也熟悉文件读写，但“读出图片文件”和“让模型看见图片”不同：后者需要 Agent 宿主，也就是管理模型会话和工具调用的程序，把图像送入模型接口。[1] 创建、协调子 Agent 也依赖宿主能力；虽然可以写命令行程序与宿主通信，作者认为这种接法比较笨重。[1]

## 2. Codemode 在宿主内部组织操作，不替代执行环境

宿主与运行 bash 的目标环境可以在同一台机器上，却有不同的信任边界；把 bash 放进隔离环境，不意味着宿主也被隔离。[1]

Codemode 让模型写一段代码，在宿主侧组合工具调用；Pi 用独立、受限的 JavaScript 运行时执行它，禁止直接访问网络、文件系统和定时器，内存也有限，外部操作必须经由提供的工具完成。[1] 因此，目标环境仍负责运行程序，Codemode 负责把宿主能提供的能力组织起来。[1]

## 3. 先让代码处理结果，不必把中间数据全交给模型

Pi 普通 bash 调用只把输出末尾 2000 行送入模型上下文，更多内容要再读溢出文件；经 Codemode 调用时，代码可以接收更大的结构化结果，筛选、组合后再返回。[1]

常见做法是先查看 5—10 条数据，了解格式，再写代码批量处理后续数据，也能安排并行调用。[1] 结果还可存入宿主上的会话记录，让同一会话的后续调用继续读取；这不等于后文所说的可靠续跑问题已经解决。[1]

## 4. 作者用真实会话展示了怎样组合这些能力

文中的代码由 Agent 在实际会话中生成，并非作者手写。[1] 一个例子是调用图像模型，既把生成的图片送回模型，也保存临时文件供后续命令使用。[1]

另一个例子抓取最多 100 条 GitHub issue（用户提交的问题或请求），让 Jev 分类模型判断情绪、挫败程度和问题类型；输入只取正文前 4000 字符、最近 5 条评论且各取前 800 字符，保存结果后，展示无错误结果中挫败评分最高的 12 条。[1] Pi 自身把工具执行并发限制为 4，其余排队，而不是代码写了并行就无限并发。[1]

还有一个游戏调试例子：代码反复读取游戏状态，让分类模型选择动作，再调用游戏命令执行，循环最多 30 步，遇到结束状态或错误等条件会提前停止。[1]

## 5. 外部工具可以按需发现，不必一开始全部展示

Pi 不把所有 MCP 工具定义直接交给模型，而是提供搜索接口，让 Agent 在 Codemode 中逐步发现需要的工具。[1]

文中的 Sentry 例子直接调用了工具，没有先搜索；但系统提示已经告诉模型该服务存在，不能理解为模型凭空发现了它。[1] 至于它是否在训练中记住了工具用法，作者明确只是推测。[1]

## 6. 两层 Codemode 叠起来，也会增加麻烦

有些 MCP 服务为适配尚无 Codemode 的客户端，自己提供代码执行接口；接入 Pi 后，就变成外层 JavaScript 再传入一段 JavaScript。[1] 作者以 Cloudflare 服务为例指出，这会带来双层 JSON 转义，即代码中的引号等符号要按嵌套层次处理，小模型容易弄混，而且内层代码不能调用外层工具。[1]

## 7. 能组合工具，还需要工具返回稳定的数据

按作者写作时的观察，MCP 配合 Codemode 仍有四处缺口：服务应返回程序好处理的 JSON；不能因为批量大小变化就改变结果结构，否则试读 5 条成功、正式批处理却可能失败；大体积二进制数据往往要借带授权的上传链接绕路；跨多个服务器搜索合适工具，也缺少良好的统一机制。[1]

此外，执行中断后怎样可靠恢复、图像和二进制数据怎样处理，以及小模型如何用好这种方式，仍未完善。[1] 作者提到保存执行快照、采用行为更确定的编程语言等可能方向，没有把它们写成已解决的问题。[1]

补充：文中 Pi 默认在启用 MCP 时启用 Codemode，也可以单独开启；以上描述针对文章当时的实现。[1]
