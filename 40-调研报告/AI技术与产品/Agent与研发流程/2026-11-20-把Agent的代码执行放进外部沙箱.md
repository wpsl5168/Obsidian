# 让 Agent 执行代码，又不把整台电脑交给它

Simon Willison｜Prime Radiant
原文：External sandboxes for coding agents；页面日期：2026-11-16。[1]

编程 Agent 一旦出错，损失可能波及它能访问的文件和网络。[1]Simon 与团队尝试把执行代码的环境单独隔离，尤其希望能更放心地试用较小、较便宜或本地运行的模型；文中介绍的是三个实验原型。[1]

## 1. Agent 留在外面，把命令送进受限环境

作者认为，逐次人工审批既慢，也容易让人疲劳后一路点同意；让另一个模型审批虽然有帮助，仍依赖模型判断正确。[1]

团队比较了“把整个 Agent 放进沙箱”和“Agent 在外、命令在内”，选择后者：减少执行中的代码修改 Agent 自身环境的机会，也让隔离边界便于审查。[1]“外部”是相对 Agent 而言，二者仍可在同一台电脑上。[1]

## 2. 用三种实现，连接同一套接口

三个原型都提供 Linux 环境：v86 在 Node.js 内通过 WebAssembly 模拟机器；Apple Containers 方案封装苹果的容器工具；Quicksand 方案把 QEMU 虚拟机和 Linux 镜像作为 Python 安装包提供。[1]

它们共用本机 API，因此客户端可以换接不同沙箱；团队也公开了协议和一致性测试工具。[1]v86 的入门演示要求 Node.js 22.19 或以上，另外两套启动示例面向 Apple silicon Mac，不能把三种实现理解成无条件跨平台。[1]

## 3. 接上沙箱，不代表所有工具都被隔离

这是原文特别强调的区别：Claude Code 只把 Bash 命令送入沙箱，原生 Read、Edit 仍能直接读写宿主电脑；Codex 接入进程和文件操作，包括 apply_patch；Pi 则替换命令执行、文件读写和搜索等工具。[1]

Pi 要求 1.5 或以上，并禁用内置工具；扩展加载失败或沙箱不可达时，会报错，而不是退回宿主执行。[1]Codex 的自动测试仅报告在 CLI 0.164.0、`codex exec` 加模拟模型条件下通过，其连接协议仍是实验性的，其他版本需要另查。[1]

## 4. 默认不联网，需要什么再放行

沙箱默认不能访问外网；启用代理后，才按目标主机和 HTTP 方法放行。[1]原文配置示例允许从 PyPI 获取安装包，访问 GitHub API 则只允许 GET 请求。[1]

代理通过配置证书检查、过滤 HTTPS 流量，代码即使忽略代理设置、尝试直连，仍会被阻断。[1]启动时开启代理后，还能在网页上实时改规则，并查看哪些请求被允许、哪些被拒绝。[1]

## 5. 调用 API 时，用占位符代替真实密钥

以 GitHub 为例，沙箱中的代码只拿到占位 token；请求经过宿主上的代理时，代理再把它换成真实凭据，代码无需直接持有密钥。[1]

但这不是“密钥绝不泄露”：获准访问的服务仍可能在响应里把凭据原样返回。[1]因此作者要求只对可信服务使用此机制，并尽量收窄可调用的方法和路径。[1]

## 6. 隔离能限制损失范围，不能消除损失

沙箱只看得到明确挂载给它的目录，但只要目录可写，Agent 仍可能破坏其中任何文件。[1]作者因此建议保留版本控制，并尽可能使用只读挂载。[1]

还有运行环境的代价：沙箱跑 Linux，项目中为 macOS 安装的 `node_modules` 或 `.venv` 可能需要在里面重装。[1]作者最后明确表示，这些仍是实验原型，尚未经过足以让人放心托付敏感任务的安全审计。[1]
