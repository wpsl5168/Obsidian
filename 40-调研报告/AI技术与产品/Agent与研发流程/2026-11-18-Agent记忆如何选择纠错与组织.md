# Agent 的记忆怎样变得有用，又怎样避免记错？

Lance Martin / Anthropic，《The components of agent memory》，2026-11-06。[1]

Agent 做完一件事，该留下什么供下次使用？文章讨论的是保存在文件等外部存储中、跨会话可读的经验，不是重新训练模型，也不是把当前聊天压缩成摘要；难处在于，当下不知道哪些经历以后有用。[1]

## 1. 留下错误还不够，要把原因验证成规则

在 CL-Bench 数据库问答任务中，每题都开新会话，答完会得到正确答案，只有记忆目录跨会话保留。[1] Sonnet 4.6 留下许多未验证猜测；Opus 4.7 开始区分已核实与待确认内容；Opus 5 则能记录经过验证的规则、依据和已发现的陷阱。[1]

提示的作用因模型而异：要求 Sonnet 4.6 答前读记忆、再验证猜测，成绩接近翻倍；但要求 Opus 4.7、Opus 5“只记失败”，反而削弱了记忆带来的提升。[1] 作者据此倾向于向较强模型说明记忆用途，让它自行判断什么值得保存，而非预设僵硬的记录规则。[1]

## 2. 把屏幕上随时能看到的东西全记下来，会拖慢任务

《宝可梦 红》的比较取自两个模型各一次运行、约一万步时的记录：Sonnet 3.7 建了 225 个文件夹、413 个文件，获得一枚徽章；Fable 5 只用九个文件加一个顶层文件，获得四枚徽章，徽章代表游戏进度。[1]

前者不断记录战斗、物品和位置，但这些状态很快过时；有连续 17 步只在整理文件，没有操作游戏。[1] 后者重点保存目标、路线和摸索出的玩法策略，不重复存屏幕每轮都能显示的钱数、位置等信息。[1] 这是不同模型的单次运行观察，不能单凭它认定少写文件就会进步。[1]

## 3. 后台回看原始记录，能把错误记忆改回来

文章把空闲时对照日志、整理记忆的计算过程称为“dreaming”。[1] 一个游戏案例中，Claude 把月见山西侧入口的精灵中心错记成在东侧，误以为已经穿过山，走下单向台阶回到原路；导航工具又没显示跌落，使它继续误判位置。[1]

研究者让后台整理过程核对原始会话，纠正地点后，Claude 重新进山并到达下一座城市。[1] 未纠正的那次运行三次掉回原路，一度想停止，系统自动催它继续后仍未到达；完全不提供记忆的那次也没成功。[1]

## 4. 文档很多时，先做互相链接的知识页，再配合搜索

这里的 wiki 是按主题整理、互相链接的知识页，让 Agent 知道信息在哪里。[1] 团队让 Opus 5 为 Stainless 约 35 万份文件、4.2 亿 token 的资料建立 wiki，用 25 个问题评估；建库从两轮增加到 128 轮会话时，只读 wiki 的成绩从 13% 升至 48%，但仍低于只搜索原文的 53%。[1]

wiki 加搜索的成绩则从 54% 升至 61%，每题约省两万 token；这里的百分比是满足评分标准的比例，不是答对题数占比。[1] 节省的是答题开销，建库也有成本：图中后台整理用量从约两百万增长到一亿二千八百万 token。[1]

## 5. 需要跨文档拼信息时更有帮助，简单查找未必值得建库

另一组 24 道并购问题中，超过一半需要结合多份文档，许多还要判断或计算；在这些题项上，使用 wiki 得分 87%，只搜索为 73%。[1] 但一个法律简报任务的大部分评分内容在单篇文档里就能搜到，wiki 没有明显收益；另一个任务甚至把 wiki 做得比原始资料还大，几乎没有提炼信息。[1]

## 6. 记忆要围绕任务保真，多人共写也会丢内容

一次合同任务中，多个 Agent 同时写共享摘要表，既概括不佳，又互相覆盖，生成的简报只包含 57 项事实中的 41 项，约 72%。[1] 团队让 Claude 反思失败、修改建库指令并重建：每份合同由一个 Agent 写独立页面，逐字引用条款；改进后这项任务的 57 项标准都能满足，不代表所有法律任务都能达到 100%。[1]

后台整理还可以跨会话补缺：另一例中，第二轮把九个指向不存在页面的链接改指已有页面，并补了三个页面，包括索引。[1]

## 7. 每轮自动加载的记忆要小，后台整理也有延迟和成本

重要笔记可以提前放进下一轮会话，免得 Agent 不知道该找什么；但错记也会随之进入每一轮，占用上下文，过长的指令还可能降低遵循程度。[1] 文中以 Claude Code 当时的做法为例：只加载 MEMORY.md 前 200 行或 25 KB，顶层充当索引，细节留在下层按需读取。[1]

作者留下的取舍是：边做边记可以立即供后续使用，却分散当前任务的注意力；后台整理减少这种打断，但结果未必及时可用，还要消耗算力。[1] 持续复查全部记忆可能不现实，是否优先检查易变信息、按访问频率安排整理，仍是开放问题；原始会话搜索可以作为底座，额外建立的 wiki 则需要持续维护，防止积累错误。[1]
