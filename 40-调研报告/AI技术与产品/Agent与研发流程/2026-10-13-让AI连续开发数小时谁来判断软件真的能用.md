# 让 AI 连续开发数小时：谁来判断软件真的能用？

原文：Harness design for long-running application development
作者：Prithvi Rajasekaran，Anthropic Labs；2026-03-24。[1]

作者想解决两个问题：让 Claude 做出更好的网页设计，以及独立完成能实际使用的应用。[1] 他尝试把写代码、做规划、检查成果交给不同 Agent，并记录了质量改善、额外成本，以及换模型后哪些安排可以删掉。[1]

## 1. 做得久会失去方向，自己检查又容易放水

作者观察到，部分模型不仅会随对话变长失去连贯性，还会因为觉得能读取的对话和材料——即上下文——快满了而提前收工。[1] 早期 Sonnet 4.5 需要清空对话，再靠交接文件传递进度；这不同于把旧对话压成摘要，但会增加流程复杂度、模型用量和等待时间。[1] 换到 Opus 4.5 后，这种提前收工明显减少，作者便取消重启，改用自动压缩。[1]

另一个问题是自评过宽：界面平庸、功能有缺陷，模型仍可能表扬自己。[1] 把验收交给独立 Agent 更便于调校，但不会自动得到严格的评审员。[1]

## 2. 先说明怎样算好设计，再让评审真正打开网页

作者把设计拆成整体协调、原创性、制作细节和可用性四项，偏重前两项；再用带详细评分的样例校准评审，使其接近自己的偏好，而非声称审美有统一答案。[1]

评审通过 Playwright 浏览器工具实际操作、截图、写反馈，生成器据此修改或换方向；每个作品迭代 5–15 轮，最长约4小时。[1] 一个博物馆网站在第9轮还是暗色首页，第10轮改成能穿过门洞参观的三维展厅。[1]

不过，评分后来会趋于停滞，作者有时更喜欢中间版本，实现也越做越复杂；评分措辞会让风格趋同，而且仅加入标准、尚未收到反馈的第一版就优于无提示基线，不能把改善全算在反复评审上。[1]

## 3. 开发前先约定“做完了”怎么验证

应用开发采用三个角色：规划器把1–4句需求扩成产品规格，但不提前写死实施细节，以免错误传到后续；实现器分阶段开发并自测；评审器实际检查界面、接口和数据库。[1] 作者还明确要求规划器加入 AI 功能，并非模型自行发现了这项需求。[1]

每阶段动工前，实现器和评审器通过文件协商交付内容及验证办法；验收覆盖产品深度、功能、视觉与代码质量，任何一项低于门槛都退回。[1] 评审最初也会浅尝辄止、发现问题却放行，作者必须多轮读日志、修改提示，才能得到较可靠的检查。[1]

## 4. 游戏终于能玩了，但多花的钱和留下的缺陷都很具体

同用 Opus 4.5、同一句游戏编辑器需求，单 Agent 跑了20分钟、花9美元；完整框架跑了6小时、花200美元，并把任务扩成16项功能、10个开发阶段，工作范围和预算都不同。[1]

单 Agent 版本能显示角色，却不响应操作；完整框架的编辑器更好用，角色也能活动。[1] 评审发现的错误很具体，例如矩形填充工具只在拖动起止点放图块，没有填满区域。[1] 但最终仍有操作顺序引导不清、角色与平台重叠、生成关卡的高墙无法越过等问题，深层功能也有漏测。[1]

## 5. 模型换强以后，原来的开发步骤未必还需要

作者曾大幅删减框架，却无法复现效果，随后改为一次移除一个组件、观察影响。[1] 换用 Opus 4.6 后，他取消逐阶段开发，把评审移到整轮构建完成后；规划器仍保留，因为没有它时模型容易少做功能。[1]

作者的判断是：模型能可靠独立完成的任务，外部评审可能只是额外开销；接近或超出其可靠能力的部分，评审才更值得付费。[1]

## 6. 更强模型仍会做出“按钮存在、功能没接”的软件

新版框架开发浏览器音乐工作站，共经历三轮构建与验收，表中总计3小时50分钟、124.70美元模型用量费用；首轮构建连续进行了2小时7分钟。[1] 这是另一个任务，不能直接与游戏编辑器的200美元当作同题降本比较。[1]

评审仍抓到音频片段无法拖动、缺少乐器操作面板、录音按钮切换却没有采集麦克风等问题。[1] 最终应用具备编曲、混音和播放功能，内置 Agent 能调用工具设置速度、添加旋律和鼓轨、调整混音，作者通过提示做出了一段短曲。[1] 但它远非专业音乐软件；实验中的 Claude 听不到声音，也限制了评审对音乐审美的判断。[1]

作者最后强调，框架里的安排是在补具体模型的短板；换模型后，应根据真实任务的运行记录重新检查哪些仍有用，而不是永久保留越来越复杂的流程。[1]
