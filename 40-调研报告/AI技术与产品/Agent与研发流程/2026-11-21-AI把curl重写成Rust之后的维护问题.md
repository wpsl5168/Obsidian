# AI 把 curl 重写成 Rust 后，维护的问题才刚开始

原文：Actual curl rewrites in rust
作者：Daniel Stenberg｜个人博客｜2026-11-17。[1]

有人用 AI 把 curl 的 C 代码重写成 Rust。[1]Stenberg 讨论的是：复刻出一个版本之后，新项目能否继续修复问题、保持兼容，跟上原项目的演进？[1]

## 1. 两个重写项目出现，其中一个声称花了 8,600 美元

文章提到 urlx，以及另一个仍叫 curl 的 Rust 项目。[1]两者都声称重新实现了 curl 和供其他程序调用的 libcurl；8,600 美元是后者公布的花费，不是作者独立核算的成本。[1]

## 2. AI 面前已经有源码、用法和测试

作者承认，Agent 几周内完成这样的工作令人惊讶。[1]但他认为，这不是从空白处设计同样的软件：curl 已有完善文档、数百个使用其接口的开源应用，以及数千个测试用例，AI 可以参照 C 代码转换，再修改到测试通过。[1]

他还把成功归因于模型多年接触 curl 代码的训练经历，这是他的判断。[1]现有 curl 则凝结了长期决策、用户反馈和反复修改；在他看来，重写者拿到的是这些积累已经形成的具体规格。[1]

## 3. 重写完成时，原项目已经继续向前走了

按作者的计数，Agent 用三周多把 185,000 行 C 转成了 340,000 行 Rust；同一时期，原 curl 合并了 300 多次提交，完成 200 多项 bug 修复，还修补了一些安全漏洞。[1]他说，这些修复当时尚未进入那两个重写项目。[1]

作者预计，再过一个月还会新增约 200 项修复，可能还有漏洞修补。[1]这是他对后续工作的预期，而他的追问是：重写项目怎样持续跟进？[1]

## 4. 长期兼容，需要团队和时间来证明

在作者看来，持续修复与改进来自用户报告问题、贡献者参与、维护者处理反馈的共同运作，不只取决于实现语言。[1]

他特别强调 curl 数十年的 API、ABI 稳定性：前者是其他程序调用它的源码接口，后者关乎已经编译好的程序能否继续与库配合。[1]新项目也可能维持这种兼容，但刚完成重写，并不能证明它能持续做到几十年。[1]

## 5. 换成 Rust 能避免一部分错误，不等于消除全部漏洞

作者给出的范围是“2026 年截至发文时”：curl 已确认 81 个漏洞，其中 14 个、即 17.3%，属于他判断使用 Rust 这类内存安全语言后“很可能可以避免”的错误。[1]

他据此推论，其余 67 个漏洞不会仅因换语言就消失。[1]这里谈的是按漏洞成因作出的反事实判断，不是已经在那两个 Rust 项目中实际检出了 67 个漏洞。[1]

## 6. 他更支持持续改进，但不知道重写项目会走多远

Stenberg 明确表示，他不赞成换成任何语言的整体重写，更相信不断打磨、迭代和重构。[1]

同时，他没有联系过这两个项目的团队，只看到了别人发来的仓库链接，也不知道它们会不会超出概念验证阶段。[1]它们可以跟着原项目平均每天约 11 次提交继续转换，也可能不处理那些问题报告，或转向其他目标；文章没有把这些项目的未来判定为失败。[1]
