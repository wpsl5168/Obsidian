# AI 写的代码改动说明太长，怎样让人愿意读？

Simon Willison｜2026-11-09
原文：Hide your slop PR descriptions behind `<details><summary>`。[1]

Simon 现在常让 Claude Code 或 Codex 发起 PR，即把代码改动提交给人检查、确认后合并的请求；他用 PR 汇集多次提交、迭代功能并记录决策，却发现 AI 写的说明越完整，自己越不想读。[1]

## 1. 信息有用，也可能让人望而却步

在他的使用经验里，Agent 会把问题、详细解决方案和验证步骤写得准确而全面，但这些内容一下子摆在眼前，阅读负担很重。[1]

他并非认定这些文字都是垃圾，而是看到明显的 AI 长文就会抗拒：读完可能比让 AI 生成它花的时间还长，即使发起任务的人就是自己。[1]

他希望先看到一段经过人挑选、认可的介绍，知道这个改动解决什么问题，再决定是否继续投入注意力。[1]

## 2. 保留全文，把细节折叠起来

他的办法是：开头只放精心挑选的简短说明，必要时配截图；完整的 AI 说明仍保留在后面，但默认收起。[1]

这用的是 HTML 的 `<details>` 和 `<summary>`：前者包住折叠内容，后者提供可以点击展开的标题；GitHub 的 Markdown 支持直接在 PR 描述或 issue 评论中使用这组标签。[1]

折叠标题写模型名，通常也写思考档位，例如“Claude Opus 5.5 Medium”，明确告诉读者后面是哪个模型生成的内容；读者先看人的精选信息，需要时再展开全文。[1]

## 3. 人负责挑选，不必每句话都亲自写

导语也可以来自 AI：有时合适的解释已经藏在长文中，只需把它挑出来。[1]

Simon 对读者的承诺是，这段开场白经过了自己的判断，值得对方花时间阅读；他没有要求把所有机器生成文字重写一遍。[1]

## 4. 好导语先说清具体变化

文中给出的实际 PR 包括这些例子：[1]

- 一个详情页原先用横向表格展示单条记录，遇到 46 列的 GitHub 仓库表就向右溢出，页面其余部分却大片空白；改动把字段改为纵向列表，导语后再附截图。[1]
- 约 220KB 的 `edit-tools.js` 原先在每个表格页、记录页和数据库页加载，连没有编辑权限的人也不例外；改后只对有权限的人，在首次与编辑功能交互时加载，其中包括鼠标悬停在编辑链接上，并不一定要点击。[1]
- 另一个 PR 增加命令行管理功能，让用户保存兼容 OpenAI 的服务端点配置，不必手工修改 YAML 配置文件；导语后直接附命令帮助输出。[1]

## 5. 改善的是阅读入口，全文仍然在

标签顺序可以记成“details-summary”：外层装完整内容，里面的 summary 是可点击的短标题。[1]

Simon 感受到的变化是，自己的 PR 不再一打开就让人面对多段 AI 说明，而所有信息仍可查阅；这是他在个人工作流中的体验，文章没有提供审查耗时或错误率的对照实验。[1]
