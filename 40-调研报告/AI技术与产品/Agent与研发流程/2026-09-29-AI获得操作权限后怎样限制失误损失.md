# AI 获得电脑操作权限后，怎样限制一次失误的损失？

原文：How we contain Claude across products
作者：Max McGuinness、Mikaela Grace、Jiri De Jonghe、Jake Eaton、Abel Ribbink｜Anthropic｜2026-05-25。[1]

Agent 是能调用工具执行任务的 AI，越能干，往往获得越多文件、命令和网络权限。[1]文章把风险拆成两件事：出错的概率，以及出错后能破坏多大范围；模型更少犯错，不代表后者也会缩小。[1]

以下是作者对当时三款产品架构、漏洞和修复的总结，不是对今天所有版本的安全保证。[1]

## 1. 反复点“允许”，不等于有人认真监督

Anthropic 遥测显示，约93%的权限请求会被批准；弹窗越多，用户越容易不再细看。[1]

自动审批也有漏判：文中报告，auto mode 能拦住约83%的过度主动行为，仍放过约17%，同时误拦约0.4%的正常命令；这些不是整套产品的安全成功率。[1]

因此，作者主张先用环境限制“能碰到什么”，再用模型约束行为。[1]防护要同时应对用户误用、模型自行越界和外部攻击，不能只防网页里的恶意指令。[1]

## 2. 不同用户，需要不同的隔离方式

claude.ai 在云端临时容器中执行代码，不在用户电脑运行；文件系统按会话存在，没有持久工作区，也不能直接访问用户本机文件。[1]这样主要保护云基础设施和不同租户，但也限制了能完成的工作。[1]

Claude Code 必须接触开发者本机，采用操作系统沙箱，即由系统强制限制程序的活动范围：允许读取、允许工作区内写入，默认禁止联网。[1]作者报告权限弹窗减少84%，并非事故减少84%。[1]

开发者仍能批准例外，熟练用户也更常在执行中纠偏；这依赖他们看得懂命令、持续注意，面对复杂命令或多个 Agent 时更难维持。[1]

## 3. 两次教训：确认太晚，以及恶意指令经用户进入

2025年中至2026年1月收到的三项漏洞报告，涉及用户确认信任前就处理项目内容。[1]其中，仓库里的 `.claude/settings.json` 可以定义自动执行的脚本，启动时先运行，之后才弹“是否信任此目录”。[1]修复是把项目配置的解析和执行推迟到用户同意之后。[1]

另一例是2026年2月的内部受控测试：研究员诱导员工粘贴看似正常的任务，里面夹带读取 AWS 凭据并外传的要求。[1]同一提示重试25次，24次完成外传；这不是对所有钓鱼攻击成功率的统计。[1]

恶意内容由用户亲自提交，依赖“用户意图”的模型防线难以识别。[1]作者给出的防护是让凭据不可读、外传路径不可用，而不是继续增加确认弹窗。[1]

## 4. Cowork 隔离代码，但不能把所有组件都当成已隔离

Cowork 面向未必懂命令的知识工作者，因此在本机虚拟出独立的 Linux 运行环境，只把选定工作区和 `.claude` 目录开放给它，凭据留在主机密钥库。[1]工作区内的文件仍可能被破坏，增加连接器也会扩展可访问范围。[1]

最初整个 Agent 都在虚拟机内，虚拟机启动失败就完全不能用。[1]后来把 Agent 调度移到主机，代码执行仍留在虚拟机，让它能继续回应并排查问题。[1]

本地 MCP 服务——供 Agent 调用其他软件的工具服务——也移到了主机，以便审计、减少依赖问题并访问本机进程；是否启用由管理员判断，不能视为同样受到虚拟机隔离，远程 MCP 不受这次迁移影响。[1]

文件可设只读、读写或读写但禁止删除；路径检查还须先解析符号链接，否则获准目录里的链接可能指向外部。[1]

## 5. 只允许访问官方域名，数据仍可能流到攻击者手里

另一项第三方披露中，恶意工作区文件藏着指令和攻击者的 API key，即账户调用凭证。[1]Claude 读取其他文件，用该 key 调用 Anthropic 文件上传接口，把文件上传到攻击者账户；网络代理看到的是获准的 `api.anthropic.com`，便放行了。[1]

这里没有逃出沙箱。[1]问题是“允许访问某域名”同时开放了该域名上的功能，却没有限制上传给谁。[1]

修复是在虚拟机内代理检查请求，只接受本虚拟机会话获配的令牌，也就是本次会话的访问凭证，拒绝攻击者自带的 key，并阻止让服务器代为抓取内容的请求头。[1]域名白名单因此需要按“授予了什么能力”来理解。[1]

## 6. 隔离更强，也可能让安全团队看不见内部活动

虚拟机挡住了 Agent，也挡住主机上的 EDR，即负责检测可疑进程与行为的终端安全软件。[1]

文章当时的补救是让管理员通过 OTLP 日志导出接口，事后拉取事件记录；作者明确说，这不等同于实时监控。[1]隔离与可观察性之间仍有代价。[1]

## 7. 工具可信，不代表它带回来的内容可信

通过审查的 GitHub 连接器，仍可能读取被投毒的 README；远程工具也可能在获批后改变行为。[1]作者因此强调持续检查工具返回内容，尽管会增加延迟，也不可能完全挡住攻击；事后日志可能只显示一次成功的合法 API 调用。[1]

作者还提醒：恶意内容写进长期记忆或项目规则后，可能每次启动都被重新加载；子 Agent 虽能隔离不可信内容，其报告也不能因为“来自自己人”就获得更高信任。[1]内部分享攻击提示用于排查时，同样可能被其他 Agent 读到。[1]

Cowork 用限权的会话令牌代表 Agent，可单独撤销而不影响用户凭据；但跨平台 Agent 应有独立身份，还是继承用户权限，文中仍视为开放问题。[1]

作者最后归纳：隔离强度要匹配用户的监督能力；本文多次出问题的是自研代理和外围逻辑，而成熟的虚拟机、容器及系统调用过滤组件经受住了这些案例中的考验。[1]
