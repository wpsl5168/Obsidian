# 让 AI 随开发流程自动工作，而不只等人来提问

Sean Goedecke｜《Continuous AI in software engineering》｜2025-07-02。[1]

作者平时遇到问题才找 AI，问完再继续工作。但测试和类型检查早已能在提交代码、编译时自动运行：AI 能否也融入这些日常环节，让人不必每次都想起去用它？[1]

## 1. “连续”指自动融入流程，不是一直生成代码

文章所说的 continuous AI，包括自动审查代码变更请求（PR）、给问题和 PR 打标签、汇总日报周报，以及编辑器里的代码补全。[1]

共同点是由既有工作流程触发，人不主动找 AI 也能获得帮助。作者把当时需要主动启动、让 Claude Code 或 Devin 完成整项修改的用法排除在这个定义之外；这并非否定这些工具的价值。[1]

## 2. 偶尔发现一个遗漏，也可能值得默认开启

让作者改变看法的是默认开启的 Copilot PR 审查。他的个人经验是，大约每五到十次审查有一次能发现自己漏掉的问题，多数审查并没有增加多少价值。[1]

一个具体例子是漏看的 n+1 查询问题，即一次操作额外引出一串数据库查询。能接受这些不太有用的审查，是因为它们很容易扫读，跳过几条的负担不大；作者想要的是随手可看的第二意见，仍由自己判断。这不是正式实验测出的检出率。[1]

## 3. 例行汇总适合交给 AI，项目异常仍要人仔细处理

作者经历的许多团队都要写周报，再向管理层逐级汇总。很多时候，它只是传达“事情还在推进”，作者认为这类协调工作可以交给 AI。[1]

但如果项目进展不顺，报告就需要人的仔细关注，不能把所有沟通都当作例行摘要。他偏好在流程中加入这种小而实用的辅助，而不是把精力都投入“全自动软件工程师”；这是他的工程取向，不是对后者可行性的否定。[1]

## 4. 把模型调用接到已有的自动化触发点

作者给出了自己参与的实现：为 GitHub Actions 原生访问令牌加入调用 GitHub Models 的权限，让已有自动化任务能够使用模型。[1]

Actions 可以在 PR 或问题被创建、代码推送到默认分支时运行，也可以按定时计划执行。因此，代码审查、分类、定期汇总都能挂到已有事件上，不必等开发者打开聊天窗口再提要求。[1]

## 5. 免费调用降低试用门槛，但并非没有限制

按文章发表时的情况，GitHub Models 向 GitHub 用户提供免费模型 API，便于尝试小型自动化，不必先解决订阅付费问题；但请求速率和一次可处理的上下文都有约束。脚注还说明，前一周已新增可选付费档，提供更高的速率限额。这些是当时的产品条件，不是今天的价格承诺。[1]

文中链接了已有的 AI Actions 集合，同时强调这种模式不绑定 GitHub：GitLab CI 搭配付费 OpenAI 服务也可以采用同样思路。[1]

## 6. 这种辅助不以“AI 完全接管编程”为前提

作者把未来五到十年由 Agent 完成全部编码当作一种可能，并未断言必然发生。他认为，即使没有走到那一步，自动检查、组织协调等辅助仍会存在；即使真的实现，更强的编程 Agent 也可能继续借助较简单的 AI 工具，就像仍会使用常规测试和类型检查一样。[1]
