# Agent 能替你部署程序，谁来拦住失控的账单？

原文：We’re going to need default hard budget caps on pretty much everything
作者：Simon Willison｜2026-10-03。[1]

Agent 让更多人能轻松做出并运行程序，但这些程序可能持续调用收费服务。[1]Simon 讨论的是：当费用超过预算，平台应该只发提醒，还是直接停止服务？他主张默认采用后者，同时允许用户明确选择取消限制。[1]

## 1. 程序容易做出来了，运行费用却不会消失

编程 Agent，以及面向普通用户、界面更容易上手的个人 Agent，降低了启动一个程序的门槛。[1]程序运行后可能调用付费 API、托管网站，或不断增加存储与计算资源的用量；这些都会产生费用，不只是使用模型本身要花钱。[1]

## 2. 发出超支邮件，不等于阻止继续扣费

文章区分了两种预算限制：“软上限”是在达到每月预算后发通知；“硬上限”则停止服务，让后续请求报错。[1]

作者举的情景是：平台午夜发来预算提醒，人还在睡觉；等早上看到邮件，失控的服务已经又花掉数百甚至数千美元。这是用来说明通知为何不足的风险情景，并非文中统计出的事故数据。[1]

## 3. 默认停服会有代价，但取消限制应由用户主动决定

反对硬上限的理由很实际：企业不希望线上应用仅因超预算就开始报错。[1]Simon 承认这一取舍，但预期多数企业和个人宁愿遇到报错，也不愿突然收到超过一万美元的账单；这是他的判断，不是用户调查结果。[1]

他的方案并非禁止超支，而是默认保留硬上限；用户若要取消，应在显眼位置明确勾选，并知道：超预算后应用不会停，后续费用仍由自己承担。[1]

## 4. 云平台开始提供这种限制，但覆盖范围要看清

Simon 特别希望 AWS 提供这项能力；他听说过有人因担心费用失控而不敢把个人项目放上 AWS，也听说过未预料风险、最终蒙受损失的经历。[1]

文章引用 AWS 2026 年 9 月 16 日的公告：升级到付费计划时，可以为项目设置月度消费上限；达到后，项目在该月剩余时间暂停。[1]不过，作者同时指出，当时文档写明新体验只向有限客户开放，不能据此理解为所有现有账户都已可用。[1]

文章还提到 Google Cloud 在当年 7 月推出 Spend Caps，允许为“项目内的特定服务”设置月度金额上限，并不等于整个账户、所有服务都受到同一个上限保护。[1]这里转述的是文章发表时的信息，不代表今天的产品可用范围。

## 5. 作者希望 Agent 在推荐服务时，也说明费用风险

文章最后提出一种理想行为：Agent 优先推荐具备硬预算上限的服务商；面对缺乏经验的新手，提醒他们不要忽视无上限服务的部署风险。[1]这是作者希望 Agent 做到的事，并非文中已经验证的现有能力。
