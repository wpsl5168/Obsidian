# 工具接上了，Agent 为什么还是用不好？

Ken Aizawa｜Anthropic
原文：Writing effective tools for agents — with agents，发布于2025年9月11日。[1]

给 Agent 接入工具，不代表它就会正确选择和使用：同一个请求，它可能调用工具，也可能凭已有知识回答，甚至误解参数。[1]文章讨论的是怎样改进工具及其说明，让模型更容易完成真实任务，而不是重新训练模型。[1]

## 1. 先减少它必须阅读和拼接的信息

把现有 API（软件调用接口）逐个包装成工具，可能让模型面对大量重复功能和无关数据。[1]作者举例：找联系人应提供搜索，而不是把整个通讯录返回，让模型逐条读；查询客户背景，可以在工具内部汇总近期相关交易和备注，减少模型来回调用及阅读中间结果的负担。[1]

建议从少量高价值工作流程起步，每个工具职责清楚、尽量不重叠，同时允许模型组合工具走不同的解题路线。[1]

## 2. 用真实任务判断工具是否好用

先做原型，向编程 Agent 提供所依赖的库和 API 文档，本地接入后亲自试用、收集用户反馈，再建立评测。[1]

题目不能只测试“会不会调接口”。[1]例如，示例任务要求调查客户一次购买被扣款三次的原因，并判断是否波及别人，比直接给出日志筛选条件更接近实际工作；复杂任务可能需要数十次调用。[1]

每题都要有可核验的答案或结果，但不能因标点、措辞不同就判错，也不能把某条工具调用路线规定成唯一正确答案。[1]

## 3. 看它实际做了什么，不只听它解释

每道题单独运行模型与工具交替调用的循环，除了成功率，还记录任务及工具耗时、调用次数、token 用量和错误。[1]token 是模型处理文本的计量单位，这里用于观察信息开销。

模型给出的理由和反馈可帮助定位问题，却不一定完整、正确，仍要检查原始调用和返回。[1]文中的历史案例是：Claude 搜索时无谓地给查询加上“2025”，导致结果偏斜；团队通过修改工具说明纠正了这个行为。[1]

## 4. 名字和说明，要让它分清对象

工具名可以包含服务、资源和动作，例如区分 Asana 的项目搜索与用户搜索。[1]但前缀、后缀的效果因模型而异，需要实测，不能照搬一种命名法。[1]

工具说明应像向新同事交接：补齐查询格式、专有术语、资源关系和输入输出要求，并用严格的数据结构约束参数；`user_id` 比含糊的 `user` 更明确。[1]用于连接模型与工具的 MCP 协议，还可通过工具注解披露开放网络访问、破坏性变更等特征。[1]

## 5. 返回少一点，但别删掉下一步必需的信息

优先返回名称、内容等有意义的信息，避免让模型反复处理难辨认的随机标识。[1]不过，后续操作需要 ID 时，仍须能取得；文章建议让工具提供简洁和详细两种返回模式。[1]

Slack 示例中，详细结果为206 tokens，简洁结果为72 tokens；简洁版只留内容，而获取线程回复需要的线程、频道等标识可从详细版取得。[1]这是一个示例的差别，不是所有工具都能节省同样比例；JSON、XML、Markdown 等返回格式哪种更好，也随任务与模型变化。[1]

## 6. 数据太多或调用出错时，要告诉它怎么继续

大结果应支持分页、范围选择、过滤或截断，并设置合理默认值。[1]文章报告 Claude Code 当时默认限制单次工具响应为25,000 tokens；这不是模型总上下文大小，也不是对今天配置的说明。[1]

截断后要提示缩小查询或翻页；参数错误应给出具体修正办法和正确输入示例，而不只是错误码或堆栈。[1]这样模型才有机会改用小范围搜索，而不是重复失败。[1]

## 7. 让 Agent 帮忙改工具，但用另一批题验收

团队把评测的完整交互记录交给 Claude Code，让它调整工具实现和说明，再重新测试；另留一批不参与优化的测试题，避免只把原题做熟。[1]

作者报告，在内部真实项目、文档和消息构成的评测环境中，这种迭代还能超过研究人员手写或 Claude 初次生成的工具，文中展示了 Slack、Asana 的测试结果。[1]这是特定内部环境的经验，并非任何系统都有同等收益的保证；随着模型和协议变化，文章主张继续用评测检查工具是否有效。[1]
