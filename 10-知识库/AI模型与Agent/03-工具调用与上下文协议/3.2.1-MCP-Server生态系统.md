# MCP Server 生态系统

## MCP Server 生态系统（2025-2026 年）

选 Server 先查**发布者、维护状态、权限边界、可重复安装方式**，再看功能。能被 Host 发现，不代表安全；列在官方仓库，也不等于生产级产品。

2026-09-08 核验：`modelcontextprotocol/servers` 明确将仓库定位为参考实现，而不是生产就绪方案；发现生态项目应查询 MCP Registry。GitHub、PostgreSQL、Puppeteer、SQLite 等早期参考实现已归档。[1] 旧教程仍能搜到安装命令，甚至官方 README 的历史配置也可能残留这些名字；必须以对应项目当前维护状态为准。

### 官方与社区 Server 分类

#### 1. 文件系统与代码管理

- **Filesystem**：官方参考实现，包名 `@modelcontextprotocol/server-filesystem`。支持配置允许目录，但“只允许这个目录”不等于“只读”。读写能力和进程 OS 权限须分别控制。
- **Git**：官方参考实现 `mcp-server-git`，提供本地仓库读、查、修改操作。即便无网络，也可能改变分支、索引或提交；不能把“本地”当低风险同义词。
- **GitHub**：新集成优先核验 GitHub 自己维护的 `github/github-mcp-server`。[3] 原 `@modelcontextprotocol/server-github` 所属参考实现已经归档，不能再标注为当前推荐。

只读代码审查应叠加三层约束：限定仓库凭据、仅暴露所需读取工具、在执行侧拒绝写操作。工具描述中的 `readOnlyHint` 是提示，不是访问控制；用户授权也不能由模型口头推断。

#### 2. 数据库与数据源

原参考 PostgreSQL、SQLite 实现已归档。[1] 不再根据相似包名推荐未知的 MySQL、BigQuery 适配器。选择顺序：数据库厂商可核验实现 → 经安全审计的社区适配器 → 官方 SDK 封装的窄业务 API。

“自然语言查库”真正的边界在数据库与服务代码：

- 只读账号限制到需要的 schema、视图或存储过程；不能给 `db_owner` 后仅在 prompt 中禁止写入。
- 对订单分析优先暴露 `sales_summary(start_date, end_date, category)`，而不是任意 `execute_sql(sql)`。参数化查询防注入，授权过滤防跨租户，两者不互相替代。
- 数据库侧设置查询超时、返回行数和扫描预算。返回分页游标与 `has_more`，避免截断后把局部结果当全量。
- 日志记录请求标识、权限主体、数据时间和行数；脱敏 SQL 参数，不保存连接密码。

旧文“Q4 增长最快”示例只有当季汇总，还按未定义的 `growth` 排序，不能算增长。本页撤下该伪代码。正确需求必须先约定环比还是同比、基期缺失/为零如何处理，再比较同口径两个期间；MCP 本身不替你完成业务定义。

#### 3. 网络与浏览器自动化

- **Fetch**：官方参考实现，用于抓取网页并转换内容；不是通用浏览器。动态渲染、登录态、交互流程需要另选工具。[1]
- **Playwright MCP**：Microsoft 维护，包名 `@playwright/mcp`，主要通过 accessibility snapshot 让模型操作网页。[4] 网页文本仍是不可信输入，浏览器登录态也不是任务授权。
- **Brave Search**：早期参考实现归档；官方清单指向 Brave 自行维护的 `brave/brave-search-mcp-server`。[1]

固定回归测试优先 Playwright 脚本或 CLI；需要多轮观察页面状态、探索流程时再选 MCP。Microsoft 项目自身也区分 CLI+Skills 的上下文成本优势与 MCP 的持续交互用途。[4] 不用同一个浏览器 profile 混放生产后台登录和任意网页抓取。

#### 4. 知识管理与协作

本地 Obsidian 集成有两条不同路径：Filesystem 读文件，或专用适配器处理 WikiLink、索引、元数据。前者依赖少，但不懂知识库规则；后者功能集中，却增加插件/API/权限面。按实际需求选，不假设一个叫 `mcp-server-obsidian` 的包就支持某个 `--vault-path` 参数。

Google Drive 旧参考实现已归档。[1] Notion、Confluence、企业云盘等具体实现的读写、附件、共享与 OAuth 范围，必须逐个查供应商文档；本页不把未经核验的命名当安装清单。检索权限应随用户身份过滤，不能用机器人能读到作为用户能读到的证明。

#### 5. 云服务与 DevOps

云管控面接入分成观察与变更两条链路。观察服务只读资源、指标和部署状态；变更服务另行审批，明确资源 ID、操作参数、预计影响与幂等键。IAM Role、Managed Identity 是身份机制，不自动保证最小权限。

禁止在教程中把泛称 `mcp-server-aws/gcp/azure/kubernetes` 直接当已核验包名。采购/上线记录至少包含真实仓库 URL、发布者、包版本或镜像 digest、支持的工具子集和可撤销凭据。首次接入只到非生产环境，观察工具不应附带“顺手修复”。

#### 6. 监控与可观测性

可观测工具应输出可追溯证据，而非直接替 Agent 归因：时间范围、采样方式、查询表达式、指标值、关联日志/trace ID、数据缺失说明。Sentry 的早期参考实现已归档；其他供应商需独立核验。[1]

示例场景：用户报告 API 延迟升高。先比较应用耗时、下游耗时、排队时间与最近部署，再检查连接池。只有延迟异常，不能直接写“连接池耗尽，增大 pool size”；若下游数据库已经过载，扩大连接池可能放大问题。这是诊断流程设计，不是本次真实故障记录。

#### 7. 通信与协作工具

消息“生成草稿”“发送”“群发”“删除”要分工具和权限。对外写操作必须返回平台消息 ID，随后读取该 ID 验证；网络超时先查幂等记录，不盲重发。Slack 旧参考实现已归档，其迁移维护者由官方清单列明。[1] Teams、邮件与 Discord 的适配器不能仅凭同名搜索结果认定官方。

### 生态数据统计：以可复核口径替代数字堆砌

旧文的“官方 12 个、社区 1000+、500+ 企业、下载 Top 3”无可追溯统计来源，本次撤下，不替换成另一组估算。

Registry 是**元数据目录**，不是代码托管平台：`server.json` 提供唯一名称、包或远程地址、启动参数等；实际软件仍来自 npm、PyPI、容器仓库或供应商远端。[2]

- Namespace 验证说明发布者控制某个 GitHub 账号或域名，不是代码审计、漏洞保证或官方推荐。
- Registry 把代码安全扫描交给包仓库和下游聚合器。内部 allowlist 仍须做权限审查、依赖审计和撤销测试。
- 官方公共 Registry 不支持仅私网可访问的私有服务；企业可实现兼容 OpenAPI 的私有目录。官方代码库不以自托管支持为目标，不能宣传“一键私有化且官方维护”。
- 本次读取的官方页面仍标注 preview，可能有破坏性变化或数据重置。缓存已批准的安装清单，不能每次执行时无审查跟随目录最新条目。[2]

### 主流 Host 支持情况：不要维护无证据的勾选表

Host 支持会随版本、账号、租户策略变化。验收至少覆盖：进程是否能启动或 HTTP 可达 → 协议协商/能力发现 → 工具列表和 schema → 一次只读调用 → 错误、超时与断线回收。需要 Resource/Prompt 的应用，还要分别验收，不能由“Tool 可用”推导全协议支持。

本地 stdio 由 Host 启动子进程，部署简单但通常继承其可访问的本机资源；远程 Streamable HTTP 更适合集中权限与审计，却增加认证、网络和服务运维成本。传输选择细节见 [[10-知识库/AI模型与Agent/03-工具调用与上下文协议/3.2.3-MCP协议架构与传输层.md]]。

### 配置示例与落地决策

#### 实例一：只读知识库问答

以下仅为 Claude Desktop 风格的配置结构示例，JSON 语法已校验；未在 Desktop 安装第三方 Server。示例路径不存在于本次环境，包须上线前固定到经过审查的版本。

```json
{
  "mcpServers": {
    "kb-reference": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/srv/kb-export"]
    }
  }
}
```

候选比较：Filesystem 适合单机少量文件；专用检索服务适合带权限过滤的多用户问答；直接 CLI 脚本适合固定离线报表。此例若只需单机检索，优先只读导出目录配低权限进程，拒绝把整个 home 或活跃 vault 交给可写 Server。上面 `args` 仅限制路径，**没有开启只读**；还要在 OS/容器挂载层强制只读，并实测写操作失败。验证 symlink/路径逃逸、隐藏文件、超大文件与敏感附件，不把一条允许目录配置当沙箱。

#### 实例二：企业 PR 审查，不自动合并

优先 GitHub 官方 Server 读取指定仓库 PR、diff、CI 结果。[3] 若既有 CI 已能完成固定检查，保留 CI 脚本；只有需要对话式跨文件查证时才增加 MCP。审查阶段凭据只读，评论发布另获授权；合并、分支删除、Actions 触发不放进同一默认批准工具集。

验收时选测试仓库，核对输出是否覆盖全部 diff（分页/截断单独报告），并验证越权仓库、写请求、撤销凭据均被拒绝。若无法证明权限隔离，退回“离线 diff 输入 + 生成建议”，不以 prompt 代替安全边界。这是部署建议，未声称本次已连接任何私有仓库或发布 PR 评论。

> .NET 类比：Host 配置更接近依赖注册与进程启动清单，而不只是 `ConnectionString`；身份、权限、生命周期和审计要分别设计。

## 从发现目录到批准安装：版本、权限与撤销闭环

2026-11-03 重新读取 Registry 的 About 与 FAQ。[2][5] 两页仍标注 preview；FAQ 规定更新元数据需要提交唯一版本号，已发布版本的元数据不可变。**元数据不可变不等于远程服务实现不可变**：同一个 HTTPS 地址后面的代码、工具集合和授权策略仍可能改变。Registry 名称、软件包版本、MCP 协议版本、Host 版本是不同维度，不能拿一个版本号替代整条依赖记录。

### 三条接入路线怎样选

- **固定 CLI／脚本**：已知输入、步骤和输出的离线任务首选。便于固定依赖和重跑，不需要为一次检索常驻 Server；缺点是调用格式、鉴权和输出合同需要自己维护。
- **本地 stdio Server**：需要交互式工具发现、数据不宜出机时考虑。必须固定包版本与安装来源，隔离进程可见目录、环境变量和网络；本地运行本身不是沙箱。
- **供应商远程 Server**：多人身份、集中升级和审计更重要时考虑。除了供应商身份，还要核服务域名、OAuth audience/scope、租户边界、工具变更通知及服务端审计。客户能访问不代表该客户的 Agent Host 支持其全部认证流程。

Registry 官方定位是供下游聚合器消费的元数据源，而非让 Host 直接信任并执行每一条发布记录。[2] 企业可在其上建立审批清单，但审批结论属于企业自己的控制面，不是 Registry 的安全担保。

### 实例三：本地 Server 升级前，复查“有效执行面”

假设知识库问答已经有一个批准版本，维护者发布新版。不能只比较 README 的功能列表；至少比较包来源和固定版本、依赖锁定信息、启动命令与参数、环境变量名称、允许目录、可见工具名及输入 schema。工具说明也要审阅，因为它会进入模型上下文；描述“只读”不能替代执行侧验证。

以下是**内部审批记录结构示例**，不是官方 `server.json`，也不是可直接安装的 Host 配置。值均为教学数据，未执行安装或联网授权；JSON 仅做语法校验。

```json
{
  "record_type": "internal-mcp-review-example",
  "publisher_namespace": "com.example/kb-reader",
  "transport": "stdio",
  "artifact": {
    "registry": "internal",
    "identifier": "kb-reader",
    "version": "1.0.0"
  },
  "capability_policy": {
    "allowed_tools": ["search_notes", "read_note"],
    "write_allowed": false,
    "network_allowed": false
  },
  "approval": {
    "state": "pending",
    "artifact_digest": null,
    "reviewer": null,
    "evidence": []
  }
}
```

审批前由可信的打包/测试流程填入真实制品摘要与证据，未填不能上线。审批记录不能直接当 OS 权限：还需只读挂载、独立低权限身份和网络限制。用一次读成功、一次写失败、一次目录外读取失败、一次隐藏凭据读取失败验证实际边界。升级发现新增写工具时，即便业务没有主动使用它，也应重新审查暴露面；不默认继承旧版批准。

### 实例四：远程 PR 审查的撤销与升级漂移

假设企业批准了某个远程代码审查服务，只允许读指定仓库。供应商可以在原地址更新服务；客户端固定 URL 不能锁住服务端实现。因此每次连接仍要检查实际协商结果与工具 schema，对新增权限、新增写工具和变更域名暂停放行。需要固定的不是一个“官方”标签，而是本次允许哪个主体、对哪个仓库、做哪类动作。

当凭据泄漏或服务被撤销批准时，分别执行：停止新调用、撤销凭据/会话、从内部允许清单移除服务、隔离缓存配置、检查未完成写请求。不能等目录删除条目再处理；本次读取的 FAQ 不提供发布者自行删除/撤回版本的通用能力。[5] 管理方可移除恶意条目，不等于用户侧撤销已生效。

验收建议：对测试仓库调用只读工具，随后撤销测试凭据，再用原凭据发起**新请求**确认拒绝；分别核新会话和现有连接，不把“关掉 UI”当断权。若曾有写请求超时，先按业务 ID 查询实际结果，避免重试造成重复评论或合并。以上是接入测试设计，本轮没有连接 GitHub 私有仓库，也未验证供应商的会话撤销实现。
