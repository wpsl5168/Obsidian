## 2025-2026 年认知架构新进展

### Anthropic 的 Agent 设计哲学

Anthropic 的《Building Effective Agents》发表于 2024 年 12 月；它讨论的是工程模式，不是特定框架的性能排名。2026-11-17 重读官方文章后，保留以下设计原则：

1. **优先使用简单方案**：不要一上来就搭建复杂 Agent 框架，先试试单次 LLM 调用 + 好的 prompt
2. **Workflows vs Agents**：
   - **Workflow**：预定义的 LLM 调用流程，编排逻辑在代码中（确定性）
   - **Agent**：LLM 自主决定执行路径（自主性）
3. **增量提升复杂度**：simple prompt → few-shot → RAG → tool use → workflow → agent
4. **Agent 循环的本质**：就是 `while not done: action = llm(context); result = execute(action); context += result`

### OpenAI 的 Agent 架构观

OpenAI 在 2025 年发布 Agents SDK 时，将 Agent 架构简化为三个核心原语：

1. **Agent**：一个配置了特定指令和工具的 LLM 实例
2. **Handoff**：Agent 之间的任务移交机制
3. **Guardrails**：输入/输出的安全护栏

这种"少即是多"的设计与 Anthropic 不谋而合——避免过度框架化。

### Google 的 Agent 白皮书

下面以编排、模型、工具三层解释 Agent 的职责划分。这是教学示意，不再把未经本轮核对的白皮书作者、日期和模型版本当作依据：

```
┌──────────────────────────────┐
│    Orchestration Layer        │  ← Agent 循环控制
│  (ReAct / Plan-Execute)      │
├──────────────────────────────┤
│     Model Layer              │  ← LLM 推理能力
│  (可替换的模型适配器)         │
├──────────────────────────────┤
│     Tool Layer               │  ← 外部能力扩展
│  (MCP / Function Call)       │
└──────────────────────────────┘
```

### 2026 年 Agent 架构八大设计模式

下面八项是阅读分类，不是官方统一标准，也不是八种互斥架构。顺序、层级、路由描述控制流；HITL 描述授权边界；多模态描述输入输出能力，可以组合使用。

#### 1. Single Agent + Tools（单智能体 + 工具）
- **适用场景**：线性任务，工具依赖简单
- **优势**：成本低、延迟小、调试简单
- **技术栈**：ReAct 模式 + Function Calling
- **典型实现**：直接模型 API 加工具分派，或轻量 Agent SDK；具体模型与工具能力另核，不沿用旧 Assistants API 作为新项目默认入口。

#### 2. Sequential Multi-Agent（顺序多智能体）
```
Agent A → Agent B → Agent C
研究员   → 分析师  → 报告员
```
- **适用场景**：流水线式工作流，每个环节需要专业化
- **实现框架**：CrewAI Sequential Tasks, LangGraph Linear Flow

#### 3. Hierarchical Multi-Agent（层次化多智能体）
```
        Manager Agent
       /       |        \
   Worker A  Worker B  Worker C
```
- **适用场景**：复杂项目管理，需要协调与委派
- **核心机制**：Manager 负责任务分解和结果聚合
- **典型框架**：AutoGen Hierarchical Chat, MetaGPT

#### 4. Competitive Multi-Agent（竞争式多智能体）
- **核心思路**：同一任务让多个 Agent 独立完成，取最佳结果
- **适用场景**：创意生成、方案比选、风险敏感任务
- **实现方式**：Parallel.ForEach + 投票/打分机制

#### 5. Collaborative Multi-Agent（协作式多智能体）
- **特点**：Agent 间可以实时通信和协商
- **适用场景**：需要动态协调的复杂任务
- **关键技术**：消息传递、共享工作空间、冲突解决

#### 6. Agent + Human-in-the-Loop（人在回路）
```
Agent 执行 → 遇到不确定性 → 请求人工审核 → 继续执行
```
- **工程目标**：把需要授权的动作显式交给人，不把模型自评置信度当批准。
- **典型模式**：Agent 处理常规，人处理例外和创意
- **实现要点**：置信度阈值、暂停/继续机制

#### 7. Router Agent（路由式智能体）
```python
# 智能路由：根据任务类型选择最佳 Agent
def route_to_agent(task: str) -> Agent:
    if is_coding_task(task):
        return code_specialist_agent
    elif is_research_task(task):
        return research_agent
    else:
        return general_purpose_agent
```

#### 8. Multi-Modal Agent（多模态智能体）
- **能力组合**：视觉理解 + 代码生成 + 工具调用。
- **应用场景**：UI 自动化、文档处理、监控分析
- **技术边界**：视觉模型识别界面，不代表具备点击权限；截图坐标、工具执行与结果验证属于宿主职责，模型名不能代替能力测试。

## 主流 Agent 框架（2025-2026）

### LangGraph

LangChain 团队出品，有状态循环 Agent 图。核心思想：把 Agent 建模为**有向图**——节点是函数或子 Agent，边是条件路由，状态在节点间流转。

下列是图结构片段，省略状态、节点实现、入口边和导入，不可独立运行：

```python
from langgraph.graph import StateGraph

graph = StateGraph(AgentState)
graph.add_node("planner", plan_step)
graph.add_node("executor", execute_step)
graph.add_node("reviewer", review_step)
graph.add_conditional_edges("reviewer", should_continue,
    {"continue": "executor", "end": END})
```

> [!tip] .NET 类比
> 这就像用 Durable Functions 编排工作流，每个 Activity Function 是一个节点。

### OpenAI Agents SDK（2025.3）

替代之前实验性的 Swarm 项目。三个核心抽象：

- **Agent**：带指令和工具的 LLM 配置（类似一个配置好的 Controller）
- **Handoffs**：Agent 之间的任务交接（类似请求转发/路由）
- **Guardrails**：输入输出校验（类似 FluentValidation）

同期发布的 Responses API 支持内置工具：`web_search`、`file_search`、`computer_use`。

### CrewAI（角色化建模）

特色是**角色化多 Agent**：定义角色、目标与工具职责。下面只保留建模示意，不据星数推断可靠性；本轮未验证其当前 SDK 构造合同。

```python
researcher = Agent(
    role="高级研究员",
    goal="找到关于AI Agent的最新技术趋势",
    backstory="你是一个有10年经验的AI研究员...",
    tools=[search_tool, wiki_tool]
)
```

> [!tip] .NET 类比
> 每个 Agent 像一个微服务，有自己的职责边界，通过消息通信协作。

### AutoGen（历史项目与迁移边界）

AutoGen 的 AgentChat 用于多 Agent 对话。微软当前文档把 Microsoft Agent Framework 定义为 AutoGen 与 Semantic Kernel 的后继方向；已有项目应按迁移指南逐项核对，不能直接把旧版本示例与新包混用。新项目先比较下文三条路线，不因历史品牌继续叠框架。

### Claude 生态

- **Claude computer_use**：GUI-Agent，能操作鼠标键盘控制桌面应用
- **Claude Code**：CLI Agent，2025 年初发布，直接在终端中进行代码开发

### 新兴框架（2025-2026）

#### Microsoft Semantic Kernel 与 Agent Framework
- **已核边界**：官方将 Agent Framework 定位为 Semantic Kernel 与 AutoGen 的后继，提供 Agent、显式 workflow、状态管理、工具及 provider 集成。
- **选型理由**：已有 .NET/Azure 工程、身份与遥测体系时值得优先试验；这不意味着所有连接器、语言实现和部署区域能力相同。
- **纠错**：删除原稿未经证实的“Semantic Kernel v2 / 2026 计划器自动优化”断言。冻结具体包版本后再验证迁移，不在综述中虚构统一版本。

#### Pydantic AI
- **发布日期纠错**：V1 官方公告为 2025-09-04，不是原稿的 2025 年 12 月；该公告的后续说明注明 V2 于 2026-06-23 发布。历史 V1 示例不能当当前主版本合同。
- **亮点**：类型化依赖注入、输出校验、可观测性与持久执行集成；类型检查约束程序接口，不能在编译时证明模型行为正确。
- **适合场景**：以 Python 类型与验证为中心的应用；业务授权、事实证据、重试预算仍需应用控制。

#### Google Agent Development Kit (ADK)
- **发布时间**：官方首次介绍为 2025-04-09，不是原稿的 2025 年 11 月。
- **核心理念**：支持确定性 workflow 与模型驱动路由，并提供开发、评测和部署能力；不限定只能用 Gemini 或 Google Cloud。
- **边界**：连接器覆盖、运行身份和读写权限须按目标集成核对，不能从“Google 生态”推断所有 Workspace 操作已授权。

#### Agent Communication Protocol (ACP，历史名词)
- 原稿对 ACP 的发布状态与抽象缺来源，本轮不将其作为当前协议推荐。
- 跨 Agent 通信与工具接入属于不同层；协议选型必须核具体规范、维护方、版本和对端实现，不能仅凭同名缩写互换。

### Model Context Protocol (MCP) 革命

MCP 的作用是标准化宿主与外部工具/数据服务的连接，不是把模型变成具备系统权限的客户端。官方介绍区分 MCP server 与 AI application/client；真正联网和执行发生在宿主侧。

原稿 `@mcp_tool` 为未指明 SDK 的伪 API，不应复制部署；直接把任意 SQL 暴露给模型也不形成安全边界。数据库工具宜按业务参数封装，例如 `lookup_order(order_id)`；租户身份由认证上下文取得，服务端固定查询与参数绑定、只读凭据、行级权限、超时和返回上限分别落实。完整 SDK 示例见 [[10-知识库/AI模型与Agent/03-工具调用与上下文协议/3.2.2-MCP-SDK开发实战]]。

**MCP vs 传统 Function Calling**：
- **传统方式**：每个模型API都有自己的工具调用格式
- **MCP方式**：宿主通过统一协议发现/调用工具，再映射成模型理解的调用形式；仍存在客户端功能、认证方式和协议版本差异。

**验收对象是宿主，不是模型名称**：分别测试能力协商、工具参数、身份隔离、错误返回、撤权后失败与调用结果回读。模型能输出合法参数，不代表工具被授权或业务写入成功。

> [!tip] .NET 类比
> MCP 与通用 API 都能减少重复集成，但协议一致不等于认证互通、权限相同或能力完整。类比只帮助理解接口复用，不能作为安全设计依据。

## 从架构分类到可验证的工程选型

### 三条候选路线与选择条件

- **直接 API＋普通代码**：适合短生命周期、少量工具、固定分支。优势是调用与成本可见、容易单测；代价是自己维护轮次、取消、结果关联和失败分类。先把它做成基线，不为“Agent 化”增加组件。
- **轻量 Agent SDK**：如 OpenAI Agents SDK，适合需要工具循环、handoff、session 与 trace，但不想手写整套调度的应用。SDK 提供机制，应用仍负责凭据、授权与业务验收。把 handoff 当控制权移交；把 agent-as-tool 当由父 Agent 汇总的子调用，不混淆返回路径。
- **显式状态图/工作流**：如 LangGraph；已有 .NET 工程可对比 Microsoft Agent Framework。适合审批暂停、长任务恢复、分支重放和可见状态机。成本是 checkpoint、状态迁移及副作用幂等的运维责任。持久化中间状态不自动提供外部 API 的 exactly-once。

选择依据是任务约束，不是框架功能清单。对同一批业务案例记录验收通过率、人工修正次数、费用、耗时、失败恢复与越权尝试。框架的公开演示不等于本团队的业务增益；两条路线都达标时，优先保留组件更少、现有团队更能维护的一条。

### 实例一：企业工单知识问答

固定链路为“身份与检索过滤 → 找证据 → 组织答案 → 引用校验”。模型只处理有权访问的结果，不能先全库检索再靠 prompt 遮盖越权内容。检索工具返回文档 ID、版本和片段；答案必须关联当前证据，没有证据就明确不足。

这里通常不需要研究员、作者、审核员三个 Agent。先用一个模型加确定性引用校验：业务门禁验证文档仍可访问、引文属于实际返回的片段，语言质量另做抽样评审。只有检索规划或跨系统查询确实需要动态选择，才扩展工具循环。失败集至少包括无答案、过期文档、同名对象、跨租户对象和来源中的提示注入。

### 实例二：跨系统权限变更

将流程拆为“读取现状 → 生成变更草案 → 校验范围 → 人工批准 → 执行 → 回读”。审批记录绑定租户、对象、动作、参数与策略版本；草案变化使旧审批失效。执行凭据不进入模型上下文，模型也无权把审批字段改为通过。

业务状态与运行状态分开：工作流节点成功仅说明函数返回，不说明权限已生效。超时可能是“未执行”或“已执行但响应丢失”；先用请求标识查询外部状态，再决定能否重试。没有服务端幂等支持时，不能凭本地重试次数保证不重复写。

下面用纯 Python 演示**审批摘要绑定的一部分**，不是完整授权系统。`approval` 必须来自已认证、可信的审批服务，`expected_tenant` 来自服务端身份上下文，绝不从用户消息或模型输出直接取。`now` 应由可信时钟提供。

```python
# kb-test: approval-binding
import hashlib
import json
from datetime import datetime

def plan_digest(plan: dict) -> str:
    payload = json.dumps(plan, ensure_ascii=False, sort_keys=True,
                         separators=(",", ":"), allow_nan=False)
    return hashlib.sha256(payload.encode("utf-8")).hexdigest()

def may_execute(plan: dict, approval: dict, expected_tenant: str,
                now: datetime) -> bool:
    if now.tzinfo is None or now.utcoffset() is None:
        return False
    try:
        expires = datetime.fromisoformat(approval["expires_at"])
        if expires.tzinfo is None or expires.utcoffset() is None:
            return False
        return (
            isinstance(expected_tenant, str) and bool(expected_tenant)
            and plan["tenant"] == expected_tenant
            and approval["tenant"] == expected_tenant
            and approval["decision"] == "approved"
            and approval["plan_sha256"] == plan_digest(plan)
            and now < expires
        )
    except (KeyError, TypeError, ValueError):
        return False
```

这是同一 Python 序列化口径的内容绑定，不是跨语言 JSON 签名规范。生产系统还必须验审批人权限、签名/可信存储、一次性消费、有效期和撤销状态；检查通过到执行之间的并发变化需要条件写入或版本锁。摘要不隐藏原文，也不证明数据真实性。

### 状态、上下文与验证的最小合同

- **状态**记录当前阶段、产物版本、待执行动作和重试预算；上下文只携带当前推理需要的信息，不能把整份运行日志当作唯一状态库。
- **工具结果**区分业务拒绝、限流、鉴权失败、网络未知与参数错误。可修复参数错误可交给模型；鉴权失败不应让模型寻找另一条绕过权限的通路。
- **多 Agent 并行**只用于无依赖子任务。写共享文件、发布或变更同一对象必须有单一提交者和冲突处理；投票多数不是事实证明。
- **恢复验收**分别覆盖同进程续跑、正常退出后恢复、突然终止和并发重复消费。只验证一个内存对象不能声称“跨进程可恢复”。
- **交付证据**保存输入版本、模型/SDK版本、工具合同、目标对象、执行回执与回读结果。更换模型后重新跑业务失败集，不只看 JSON 解析通过。
