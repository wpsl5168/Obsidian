# Agent Loop（智能体循环）

> 版本边界：第1—7节保留历史概念与访谈笔记；涉及人物、用量和市场统计的断言本轮未逐条复核。2026-11-03 的来源复核及工程补充见第8节，不能将本页 updated 日期理解为全文事实已刷新。

> 一句话定义（Simon Willison）：**An LLM agent is something that runs tools in a loop to achieve a goal.**
> 智能体 = 一个 LLM 在循环里反复调用工具直到达成目标。用好它的艺术，全在于"为它精心设计工具和循环"。

## 1. 概念骨架：什么是 agent loop / agentic loop

最小定义（Dax Raad，OpenCode 创始人原话）：
> "它就是一个能访问一些工具的 LLM。它思考该调哪个工具 → 调用工具 → 把结果当成新输入 → 再思考 → 再调工具 → 再拿结果当输入……不断重复，直到它自己判断任务完成。"

拆成执行循环（业界通用 plan–act–observe 模型）：

```
目标(goal)
  │
  ▼
┌─────────────────────────────────────────┐
│  LOOP（直到任务完成或触达停止条件）        │
│   1. Think/Plan  推理下一步、选工具        │
│   2. Act         调用工具(shell/API/...)   │
│   3. Observe     把工具结果作为新输入回填    │
│   4. Evaluate    判断是否完成 → 继续 or 停  │
└─────────────────────────────────────────┘
  │
  ▼
结果(交付/停止)
```

关键区别：
- **简单 tool calling ≠ agent**：单次"模型决定调一个函数"不是 agent。Agent 的本质是 **observe→re-plan 的迭代闭环**——拿结果当新输入再想一轮。
- **机制上 LLM 返回 `tool_calls` 数组**（函数名+参数）而非纯文本，宿主程序执行后把结果塞回上下文，进入下一轮。

经典警句（Solomon Hykes，Docker 创始人）：
> "An AI agent is an LLM **wrecking its environment** in a loop."（一个 LLM 在循环里折腾它的环境）——点出 loop 的威力与危险并存。

## 2. coding agent 为何是 loop 的最佳载体

Simon Willison 的核心论点：**coding agent 本质是"暴力求解器"**。
- 只要能把问题**归约成一个清晰目标 + 一组能朝目标迭代的工具**，coding agent 往往能"暴力"撞出有效解。
- 最适合 agentic loop 的问题特征：
  1. **成功标准清晰**（有明确的对/错信号）
  2. 解法需要**试错**（枯燥的、要试很多变体）
  3. 你心里冒出"这里我得试一堆变体"——就该设计一个 loop
- 黄金场景：**调试**（跑失败的测试找根因）、**性能优化**（让 agent 基准测试不同索引/SQL）、**依赖升级**（有测试套件兜底，让它升完跑测试自愈）。

设计 loop 的三个工程关键（Willison）：
1. **YOLO 模式的安全性**：默认每条命令都要批准会废掉效率；解法是放进**沙箱**（Docker / 别人的电脑如 Codespaces / Code Interpreter），锁定出站只到可信主机防数据外泄。三大风险：坏 shell 命令毁文件、源码/密钥**外泄攻击**、拿你机器当**跳板攻击**别人。
2. **选对工具**：优先 **shell 命令** 而非 MCP——LLM 极擅长跑+迭代 shell；用 `AGENTS.md` 给一个清晰示例，agent 能外推到其他用法。
3. **收紧凭证**：用测试/staging 环境、给死预算上限（他举例：为调查 Fly.io 冷启动单开一个组织 + $5 预算 + 仅限该组织的 API key）。

## 3. Boris Cherny（Claude Code 创建者）的观点

身份：Anthropic Claude Code 创建者兼负责人。前 Meta Principal Engineer（5 年）。Claude Code 2024-09 起步只是个终端原型 side project，现已占 **约 4% 的 GitHub 公开提交**，日活上月翻倍。

### "Loops are the future"——核心主张
- **Loop 的实操定义**（三阶段）：loop 是"**你写的一个小程序，它代你 prompt coding agent → 读取 agent 产出 → 判断任务是否完成**，没完成就继续喂"。即把 agent 本身当成可被外层程序调度的原语。
- **"Coding is solved（编码已被解决）"**：对他做的这类工作而言，编码已解决；他本人 **6 个月+ 没手写过一行代码**。
- **"software engineer"头衔可能年底消失**，融解为更接近"**builder（构建者）**"——设计师/PM/经理都开始自己 ship 代码。

### 个人工作流（被广泛传播的"创始人自用设置"）
- **并行会话是地基**：本地开多个 Claude Code tab（按项目重命名 tab 保持心智上下文），**外加 claude.ai/code 上 5–10 个 web 会话并行**；本地会话可推到 web、任意设备接力。
- **隔夜跑"几千个" sub-agent**：在 Claude App 左侧 code tab 挂一堆会话，让 agent 军团overnight 做"更深的活"。
- **始终用 plan mode**；**给 Claude 一个能自我验证的方式**（测试/可运行的检查）——呼应 loop 必须有"verify"阶段。
- 偏用更大更慢的模型（Opus）：虽然比 Sonnet 大且慢，但**要 steer 的次数更少、工具调用更强，最终往往更快**。

### 产品哲学（反直觉原则）
- **给团队无限 token 反而做出更好的 AI 产品**：token 充裕让产品决策更对。
- 个人插曲：曾短暂离开 Anthropic 加入 Cursor，**两周后回归**。

## 4. Dax Raad（OpenCode 创建者）的观点

身份：OpenCode（terminal-first 开源 coding agent，2024-07 launch）+ Zen（质量优先的推理 API）创建者；Terminal 联合创始人、SST 创建者。OpenCode 数月内 MAU 从 ~65 万冲到更高量级，是增长最快的 AI 开发者工具之一。

### 为什么开源
- **模型每天都在出新**，单个开发者测不过来；开源让 Gemini/各模型的**重度用户帮忙发现 quirk、修兼容**。
- 反例：Claude Code 只跟 Anthropic 模型深绑——开源对它没社区收益。
- **"OpenCode 是防厂商锁定的横向层"**：模型切换太快，横向兼容层有结构性价值。
- 增长杠杆：Anthropic 一度封锁 OpenCode 与 Claude Code 的集成，OpenCode 转身联手 OpenAI 等其他模型商，**把封锁变成增长**。

### 最尖锐的观点：别骗自己"感觉高效 ≠ 真的高效"
- **"The feeling of productivity is not the same as actual productivity."** 用 AI 工具的爽感，常常不等于真实产出提升。

### 反 benchmark 立场（很犀利，值得记）
- **红旗信号**：任何 AI coding 产品发布时如果说"我们在某 benchmark 上第一名"，基本可判定在扯——因为**永远是个你没听过的 benchmark**。
- 90% 的 benchmark 不反映真实工作（迷宫题 ≠ 日常编码），多由不熟生产工作流的研究员造。
- 用户真正能感知的差异其实是**产品体验（响应速度、易用）**，却被归因成"AI 更强"。

### "迷信行为"类比（pigeon superstition）——金句
> 鸽子实验：鸽子会发展出迷信行为，因为它注意到"我往这边走/做这个头部动作时，食物就来了"。
- LLM 行为**随机不可预测**（今天神、明天废），用户给性能波动编出**虚假因果**。
- 聪明工程师更糟：会给迷信**建出一套智力上的正当化**（"OpenCode 在这些情况就是比 Claude Code 好"，尽管底层逻辑几乎一样）。
- **"聪明工程师在对这些模型/工具发表意见时，本质上是在搞占星术。"** 整个行业从确定性思维被迫进入非确定性系统，却还想用旧的理性方式解释它。

### 产品哲学
- **terminal-first**：消除编辑器↔浏览器切换摩擦、直接操作文件系统、给 power user 更高天花板。
- **"轶事胜过数据"**：亲自把工具当 daily driver 用一两天来评判，而非看指标。

## 8. 工程补充：停止、验收和跨会话交接

### 8.1 本次核验范围与历史观点的边界

2026-11-03 重读 Simon 的原文及 Anthropic 的两篇工程文章。[A][B][C] 本节补的是可实现的运行控制，不是对前文全部访谈的重新考证。第3—5节中的人员履历、使用量、市场份额、并行数量及“编码已解决”等说法保留为原笔记中的历史观点，**本轮未逐条复核，不能作为当前统计或采购结论**。

Anthropic 区分预先编码路径的 workflow 与由模型动态决定步骤的 agent，并建议有必要才增加复杂性。[B] 因而“单次 tool calling 不算 agent”只是本页采用的工作定义，不是统一协议判定；某个 Agent 恰好一轮解决任务，也不改变其支持迭代的架构。模型返回格式同样依供应商而异：`tool_calls` 不是所有 API 的共同字段，宿主应做消息协议适配。

### 8.2 内层工具循环与外层任务监督分开

- **内层**：读取本轮上下文 → 模型提出动作 → 宿主校验权限/参数 → 执行 → 回填工具结果。模型只提出动作，权限判断属于可信控制面。
- **外层**：维护验收项目、剩余预算、授权状态、产物版本与恢复点；决定继续、等待审批、限额暂停或验收完成。模型生成一句“完成了”不能直接推进终态。
- **持久化交接**：保存当前 commit/产物摘要、已验证项、失败命令和下一项。只存聊天摘要不足以证明现场可运行；新会话应重新读取真实目录与 Git 状态，并运行最小冒烟检查。[C]

完成条件是“原始要求全部验证通过”，不是“当前计划中的几步已经做完”。一个循环可能正常停止但任务仍未完成：预算耗尽、权限不足、依赖失效、写操作结果未知都需要各自状态，不能统一包装成成功。

### 8.3 可执行的终态判定参考

下面是 Python 3.11 标准库纯函数，演示外层控制状态；不包含模型请求、沙箱或工具执行器。`evidence` 必须由可信验证器收集，不能直接采用模型生成的字典；每项证据绑定本次产物摘要，修改产物后旧证据自动失效。摘要应从真实产物计算，而非由模型填写。

```python
from collections.abc import Mapping


def decide_next(required, evidence, artifact_sha, *,
                steps, limit, authorized, unknown_write=False,
                model_done=False):
    if type(steps) is not int or type(limit) is not int:
        raise ValueError("steps and limit must be integers")
    if steps < 0 or limit < 1:
        raise ValueError("invalid step budget")
    if not isinstance(artifact_sha, str) or not artifact_sha:
        raise ValueError("artifact identity is required")
    if not isinstance(required, (set, frozenset)) or not required:
        raise ValueError("nonempty acceptance criteria required")
    if not all(isinstance(k, str) and k for k in required):
        raise ValueError("criteria IDs must be nonempty strings")
    if not isinstance(evidence, Mapping):
        raise ValueError("evidence must be a mapping")
    if not all(type(x) is bool for x in
               (authorized, unknown_write, model_done)):
        raise ValueError("flags must be booleans")
    if not authorized:
        return "blocked_authorization"
    if unknown_write:
        return "reconcile_before_retry"
    passed = True
    for key in required:
        item = evidence.get(key)
        if (not isinstance(item, Mapping)
                or item.get("passed") is not True
                or item.get("artifact_sha") != artifact_sha):
            passed = False
            break
    if passed:
        return "completed"
    if steps >= limit:
        return "paused_budget"
    if model_done:
        return "verify_required"
    return "continue"
```

这里 `completed` 优先于已耗尽步数，是因为本例只限制**后续执行次数**：已经产生且被验证的结果不因最后一轮正好用完额度而失效。若任务含硬截止时间、费用上限或额外安全条件，应把它们加入可信验收与调度器；步数上限不等于金额上限，函数也不会中断正在运行的工具。工具超时需要执行器单独处理，取消远端写请求也不保证写入没有发生。

### 8.4 实例一：依赖升级后的失败测试修复

输入是一个测试失败的仓库和明确升级范围。先在隔离工作副本中复现失败，锁定依赖与基准 commit；禁止改验收定义来取得“全绿”。每轮只选择一个最小修复，运行对应回归，再跑整体验收。记录原始退出码和失败用例，不能仅让模型总结“测试正常”。

验收至少区分：目标依赖版本已安装、原故障测试通过、其他回归通过、需要的用户流程通过。若网页任务只跑了 API 单测，浏览器操作仍未覆盖，就不能把该项证据写成通过。[C] 进入新会话后先检查工作树和已记录 commit 是否一致；发现并发修改要重新验证，不能沿用旧产物的测试状态。

候选方案：步骤固定、失败处理明确时用 CI workflow；根因未知且需要试错时加受限工具循环；确实要跨会话、多分支恢复时才引入持久化编排。不是只要用了大模型就必须上多 Agent。这个实例是工程设计，不是本轮升级某个真实软件的结果。

### 8.5 实例二：创建工单超时，先核结果再重试

模型请求创建工单，HTTP 超时，不能把它当作“未创建”。外层把状态置为 `reconcile_before_retry`，保存平台支持的幂等键、请求摘要及目标空间，随后用可信查询检查是否已经产生工单。查到唯一且参数相符的结果，再读取它的实际字段验收；查不到也须先确认查询覆盖、最终一致性和平台的幂等合同。

如果平台没有可查询幂等键，只能依据可靠业务标识辅助核对；仍不确定时暂停，不盲目循环创建。审批已过期或参数发生改变则重新审批，不能复用旧批准。这里解释的是未知结果的控制策略，不保证任意 API 实现 exactly-once。

对比另一种失败：只读文档查询遭遇临时网络中断，可在有限次数、退避和整体超时下重试；写入超时则多了“可能已执行”的状态。把两种错误放入同一自动重试器，往往比模型选错工具更危险。
