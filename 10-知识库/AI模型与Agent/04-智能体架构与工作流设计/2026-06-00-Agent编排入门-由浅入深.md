## 第 0 层：为什么需要"编排框架"

最原始的用法：你给大模型发一句话，它回一句话——**一次 LLM 调用**，直接调 API 就行，不需要任何框架。

但很快不够用：
- 模型不知道今天天气 → 得让它**调工具**（查天气 API）
- 一个问题要分几步 → 先查资料、再总结、再翻译
- 一步错了要重试、要分支判断、中途要人确认

这时你在写一堆"什么时候调哪个、结果怎么传下去、出错怎么办"的胶水代码。**编排框架就是来管这摊事的**——管理 agent 之间、步骤之间的控制流和数据流。

> **核心定义**
> - **Agent** = LLM + 工具 + 记忆 + 能自己决定下一步做什么
> - **编排（Orchestration）** = 管多个 agent / 多个步骤怎么协作

---

## 第 1 层：从"一个 agent"到"多个 agent"

先从单个 agent 做起。只有评测证明任务确实需要独立上下文、不同权限或可并行的子任务时，再拆给多个专职 agent；单纯增加角色名不等于提高正确率。例如把只读检索与有写权限的执行分离，比让三个模型重复讨论更容易验证权限边界。

**问题来了：这个团队怎么协作？** 谁先干、谁后干、谁说了算、信息怎么传——这就是编排的核心。历史上出现了**四种协作思路（范式）**，这是理解整个赛道的总钥匙。

---

## 第 2 层：四种编排范式（用团队比喻记）

**① 对话式（Conversation）— 像开会**
几个 agent 围一桌用"说话"协商，A 说完 B 接话，一个主持人决定谁发言。灵活，但像真实会议——可能跑偏，不太可控。
→ 代表：**AutoGen 的对话协作模式**。OpenAI Agents SDK 的 handoff 则是将控制权委派给另一个 agent，不能简单等同于“群聊”。[2][3]

**② 图 / 状态机（Graph）— 像流程图**
画一张明确的流程图：这个框做完→根据结果走左还是走右→可以绕回去重做。控制路径显式定义，节点仍可包含自主决策；图本身不保证模型结果可复现，断点续跑还需要正确配置持久化与恢复标识。[4][5]
→ 代表：**LangGraph、微软 MAF Workflows**

**③ 角色扮演（Role）— 像公司分工**
给每个 agent 发"工牌"：你是研究员、你是文案、你是审核。按角色自然分工，上手最直观。
→ 代表：**CrewAI**

**④ 事件驱动（Event）— 像流水线传送带**
每步处理完"扔出"一个事件，下一步"接住"继续干。天然适合数据加工流水线（尤其 RAG）。
→ 代表：**LlamaIndex Workflows**

> 这四种思路是学习用的切面，不是互斥分类；一个框架可以同时支持图、事件和角色分工。

## 第 3 层：主流框架认识（先知道各自解决什么）

### 微软系：沿现有工程边界选择
- **Semantic Kernel (SK)** — 已采用 SK 的系统先盘点插件、模型连接器和生命周期要求，不因为新框架出现就直接重写。
- **AutoGen** — 既有多 agent 实现的迁移应核 API、消息协议与运行状态兼容，不把框架间概念相似当成无缝升级。
- **Microsoft Agent Framework (MAF)** — 官方定位为 SK 与 AutoGen 的直接后继，结合 agent 抽象、企业能力与显式 workflow。2026-10-06 核对的官方页提供 .NET、Python、Go 入口，并明确 Go 处于 public preview；不能沿用旧稿“整个框架仍 Preview”或“某框架唯一支持某语言”的笼统结论。生产成熟度须按语言、包及所需功能分别核验。[1]

### LangChain 系：组件、控制流与观测分工
- **LangChain** — 做"积木"：把模型、工具、检索打包成标准组件。入门最常见。
- **LangGraph** — 做"流程图"：适合需要显式状态、分支、暂停恢复的流程；不是所有 agent 都需要图框架。
- **LangSmith** — 做"运维"：查看请求、工具调用与执行轨迹；可观测性不等于能读取模型真实内部思考。
- 三者配合：**组件（LangChain）+ 编排（LangGraph）+ 运维（LangSmith）**，原型到上线一条龙。

### 其他主流
- **CrewAI** — 角色与任务分工是易于理解的入口；是否容易维护需要用自己的业务样本验证，不作“上手最快”的统一排名。
- **OpenAI Agents SDK** — 提供 agent、tool、handoff 等抽象；官方支持非 OpenAI provider 接入，并非强绑定单一模型厂商。模型可接入不代表 structured outputs、工具调用、usage 与 tracing 的行为完全一致，需逐项测试。[2][3]
- **LlamaIndex Workflows** — 事件驱动可用于文档加工与检索流程；有固定 ETL 步骤时也应比较普通任务队列，不默认它是唯一首选。

## 第 4 层：初学者怎么动手

### 学习路径（由浅入深）
1. **先理解概念**，别急着上框架。搞懂三个词：
   - **tool calling**（模型调工具）
   - **agent loop**（think→act→observe 循环）
   - **state**（贯穿全流程的共享状态）
2. **第一个框架二选一**：
   - 需要显式分支、持久化与人工审批 → 评估 **LangGraph**。
   - 以工具循环和专家委派为主 → 评估 **OpenAI Agents SDK**。
3. **从单 agent 做起**：先让一个 agent 会调一个工具（如查天气），跑通。
4. **再加第二个 agent**：体会"协作"和"信息传递"。
5. **再学持久化 + 人工介入（HITL）**：让流程能暂停、等确认、再继续——这是生产级 agent 的门槛。

### 避坑提醒
- 别一上来学 LangChain 一堆 Chain 抽象，容易被"过度封装"绕晕。直接从 LangGraph 的 node/edge 入手更清晰。
- 框架与发布状态会变，先吃透控制流、状态与权限边界，再按官方文档核所用版本。
- **MCP**（Model Context Protocol）这个词会反复遇到——它是给 agent 统一"接工具"的标准协议，值得早点了解。

## 关键概念速查

- **Agent**：能自主决定下一步的 LLM + 工具 + 记忆
- **Tool / Tool calling**：模型调用外部能力（API、检索、计算）
- **Agent loop**：think（想）→ act（调工具）→ observe（看结果）→ 循环
- **State（状态）**：贯穿整个流程、各步骤共享读写的数据
- **Orchestration（编排）**：管多 agent / 多步骤的协作顺序与数据流
- **Supervisor / Handoff / Swarm**：多 agent 的三种组织方式（中心调度 / 互相转交 / 无中心蜂群）
- **HITL（Human-in-the-loop）**：流程中途暂停等人工确认再继续
- **Checkpointing**：把每步状态存下来，支持暂停-恢复、故障重跑
- **MCP**：给 agent 统一接工具/上下文的标准协议

## 第 5 层：用两个业务实例判断是否需要框架

### 实例一：只读知识库问答

最小链路是“识别用户身份 → 按权限检索 → 生成带引用回答 → 核引用是否存在”。先用普通函数串起来；检索零命中就回答证据不足，不让模型虚构引用。只有需要反复改写查询、查询多个数据源并比较结果时，才引入有界 agent loop。

关键状态至少包括问题、租户/用户标识、允许读取的文档集合、命中文档版本及引用。权限过滤必须由检索后端执行，不能只在 prompt 里写“不要看其他部门文件”。两个问题共用向量库也不能共用无租户边界的缓存。

验收分三类：正常命中要能点回原文；零命中要明确拒绝臆测；越权文档即使相似度最高也不能进入模型上下文。这里不需要为了“多 agent”拆成研究员、作家、审核员；先验证一个流程能否可靠完成。

### 实例二：生成配置变更，但审批后才执行

最小链路是“只读诊断 → 生成候选 patch → 测试 → 展示具体差异 → 审批 → 单独执行节点 → 读取目标验证”。审批必须绑定本次 patch、目标环境与资源，而不是给会话永久放行。拒绝与过期是结束分支，不是换工具重试的信号。

使用 LangGraph 时，`interrupt()` 恢复会从所在节点开头重跑；审批前发送通知、创建工单等动作可能重复。把副作用拆到后继节点，并给外部操作建立持久化幂等键。仍需处理“外部操作成功但本地记账失败”的窗口：先读取外部状态，再决定是否重试，不能仅靠内存 set 声称 exactly-once。[4]

以下是 **Python 标准库教学示例**，只演示审批与内容绑定、过期拒绝；不调用模型、不发布任何配置。`approval` 必须来自受信审批服务，不能采用模型生成的字典。身份认证、角色授权、防重放与执行记账由外层负责，哈希本身不是签名。

```python
import hashlib
import hmac
import json

def fingerprint(change):
    raw = json.dumps(change, sort_keys=True, ensure_ascii=False,
                     separators=(",", ":"), allow_nan=False).encode()
    return hashlib.sha256(raw).hexdigest()

def approved(change, approval, now):
    if not isinstance(approval, dict):
        return False
    expiry = approval.get("expires_at")
    digest = approval.get("change_sha256")
    return (
        approval.get("decision") == "approve"
        and type(expiry) is int and expiry > now
        and isinstance(digest, str) and digest.isascii()
        and hmac.compare_digest(digest, fingerprint(change))
    )
```

建议 `change` 同时包含 `resource_id`、`environment`、`base_revision`、候选内容与请求标识。改其中任一字段都应重新审批；同一内容的新请求也不复用旧批准。`now` 由服务端时钟提供。这里使用整数时间戳是示例合同，不是通用审批API格式。

### 三条路线如何取舍

- **普通函数 + 显式状态**：步骤少且固定时优先；依赖少、测试直观，但持久化与补偿需要自行实现。
- **OpenAI Agents SDK**：模型自主工具选择、专家 handoff 是主要需求时评估；外部持久化、授权和 provider 差异仍要自行验收，不能把 handoff 当成权限提升。[2][3]
- **LangGraph**：分支、循环、等待审批、故障恢复是主要难点时评估；代价是状态 schema、reducer、checkpointer 与重放纪律。`InMemorySaver` 只在进程内保存，重启恢复需要持久化后端。[4][5]

本页的推荐顺序是普通函数建立基线，再按实际失败模式引入 SDK 或图；已有 .NET 工程同时对照 Microsoft Agent Framework 的对应能力，不为统一技术栈盲迁移。[1]

### 上线前最低验收

- 每个外部调用有超时；总步骤与重试次数有上限；不重试权限拒绝。
- 暂停后重启进程能恢复正确任务，用户/租户隔离和审批身份仍有效。
- 拒绝、过期、patch 变更与目标变更均不能执行。
- 重复回调、节点重放不会重复产生副作用；外部结果不明时进入核查分支。
- 日志能关联任务、节点、工具结果与资源版本；默认不写密钥或整段敏感材料。
