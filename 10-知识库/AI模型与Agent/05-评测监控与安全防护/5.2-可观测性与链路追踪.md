# 可观测性与链路追踪

> [!note] 说明
> 本文保留指标、Trace、工具与生产实践结构。2026-11-17 核对官方文档，新增隐私采集边界与两个业务实例；滚动文档、伪代码和本地测试分别标明，不把旧价格或示意数据当实测。

## 核心概念

### 为什么 LLM 应用需要专门的可观测性？

传统微服务可观测性（Metrics / Logs / Traces 三支柱）在 LLM 应用场景下严重不足：

| 维度 | 传统微服务 | LLM 应用 |
|---|---|---|
| **延迟** | 毫秒级，确定性 | 秒级，波动大（streaming 尤其） |
| **输出** | 结构化 JSON / 状态码 | 非结构化自然语言，需要质量评估 |
| **成本** | 按计算资源计费 | 按 Token 计费，成本与输入长度强相关 |
| **调用链** | HTTP/gRPC 调用 | Prompt → LLM → Tool Call → LLM → 输出（多轮嵌套） |
| **调试** | 看日志、看堆栈 | 先看结构化执行证据；正文按授权脱敏采样，不要求模型隐藏推理 |
| **质量** | 功能对/错 | 回答"好不好"是模糊的，需要评分体系 |

> [!info] .NET 类比
> Application Insights / OpenTelemetry 可以承载应用自定义指标与链路；LangSmith / Langfuse 补充面向 LLM 的评测、提示词与成本工作流。不要把“是否有专用 UI”误写成底层 APM 无法表达这些数据。

### 核心指标体系

LLM 应用可观测性需要追踪的指标分三层：

```
┌─────────────────────────────────────────────┐
│  业务层指标                                   │
│  ├─ 用户满意度（点赞/踩）                     │
│  ├─ 任务完成率                                │
│  └─ 回答质量评分（LLM-as-Judge）              │
├─────────────────────────────────────────────┤
│  应用层指标                                   │
│  ├─ Token 消耗（输入/输出/总计）              │
│  ├─ 成本（按模型计费单价折算）                │
│  ├─ 延迟（TTFT / Total Latency / Streaming） │
│  ├─ 工具调用成功率                            │
│  └─ Retrieval 命中率（RAG 场景）              │
├─────────────────────────────────────────────┤
│  基础设施层指标                                │
│  ├─ API 可用率 / 限流情况                     │
│  ├─ GPU 利用率（自部署场景）                   │
│  └─ 缓存命中率（Semantic Cache）              │
└─────────────────────────────────────────────┘
```

## 关键机制与原理解析

### 一、LLM Trace 的数据模型

LLM 应用的 Trace（链路）与传统分布式追踪的 Span 模型类似，但增加了 LLM 特有的语义。下图仅表示字段组织：Token、时延、评分均为演示占位，费用不能由图中的数值推断。正文采集须显式启用，生产默认不记录完整输入输出：

```
Trace（一次完整用户请求）
├── Span: Chain/Agent（编排层）
│   ├── Span: Retrieval（检索）
│   │   ├── Span: Embedding（向量化查询）
│   │   └── Span: VectorDB Search（向量搜索）
│   ├── Span: LLM Call（第一次模型调用）
│   │   ├── input: prompt（含 system + user + context）
│   │   ├── output: completion（含 tool_calls）
│   │   ├── model: <实际响应模型标识>
│   │   ├── tokens: <供应商usage经口径转换>
│   │   ├── cost: <价格版本与用量计算结果>
│   │   └── latency: <单调时钟测量>
│   ├── Span: Tool Execution（工具调用）
│   │   ├── tool: sql_query
│   │   ├── input: "SELECT TOP 10..."
│   │   └── output: [{...}, {...}]
│   └── Span: LLM Call（第二次模型调用，处理工具结果）
│       ├── input: prompt + tool_result
│       ├── output: final_answer
│       └── ...
└── Metadata
    ├── user_id, session_id
    ├── feedback: thumbs_up
    └── eval_score: <评分及评审器版本>
```

> [!tip] 对比 SQL Server
> 这就像 SQL Server Profiler / Extended Events 追踪一条 SQL 的执行计划——你需要看到的不只是"这条查询花了 3 秒"，而是"它在 Index Scan 上花了 2.5 秒，因为缺了一个覆盖索引"。LLM Trace 同理：你需要看到哪个 Span 消耗了多少 Token，Prompt 组装是否合理。

### 三、生产环境监控最佳实践

#### 1. 成本监控与预警

```
// 伪代码：Token 成本追踪 Dashboard 指标
daily_cost = SUM(每次模型调用按输入/缓存/输出各自口径计价)
cost_per_query = AVG(trace.cost) GROUP BY endpoint
cost_anomaly = daily_cost > 7d_moving_avg * 1.5  // 成本异常告警

// 类比 SQL Server：就像监控 DTU 消耗和查询开销
// 你不会让一条未优化的查询烧光你的 Azure SQL 预算
// 同理，错误循环可能增加调用；按实测用量定位，不预设增长倍数
```

#### 2. 质量监控（在线 Eval）

```
// 生产环境持续质量监控
对每个 trace 的输出，异步执行：
  1. 用 LLM-as-Judge 评分（1-5 分）
  2. 检测幻觉（Faithfulness Score：输出是否有 Context 支撑）
  3. 检测有害内容（Safety Score）
  4. 记录用户反馈（显式 thumbs up/down）

告警条件：
  - 质量评分 7 日滑动均值下降 > 10%
  - 幻觉率 > 阈值（如 15%）
  - 用户踩/赞比 > 0.3
```

#### 3. 延迟优化追踪

**TTFT（Time To First Token）** 是用户体验的核心指标：

| 优化手段 | 效果 | 追踪方式 |
|---|---|---|
| Prompt 缓存（Anthropic / OpenAI） | 取决于可缓存前缀、命中与负载，须A/B测量 | 按供应商usage记录缓存读写Token |
| 语义缓存（Semantic Cache） | 相似查询直接命中 | 追踪 cache hit rate |
| 流式输出（Streaming） | 感知延迟大幅降低 | 追踪 TTFT vs Total Latency |
| 模型路由 | 简单问题用小模型 | 追踪不同模型的调用比例 |

## 五、采集合同：先保证能信，再增加字段

### 三条部署路线

- **已有 OTel/APM**：复用 Collector、告警与访问控制，在模型调用处补语义属性。优点是不再维护第二套遥测链路；代价是 LLM 评测、提示词版本与数据集功能需要额外实现或集成。
- **Langfuse 自托管**：适合需要可审查的数据路径与专用 LLM 交互界面的团队。自托管不自动满足合规：浏览器、模型 API、评分服务、备份和 exporter 的出站地址都要核对，日志平台本身也必须按租户隔离。
- **LangSmith 等托管平台**：适合已有框架集成、希望减少平台运维的场景。先验证敏感数据是否离境、保留/删除策略、项目权限和成本口径，再谈接入速度。本轮不比较未核的套餐价格与性能排名。

验收不是“控制台出现一条 trace”，而是一次请求中检索、模型、工具、重试和最终判定能否正确关联；随后模拟 exporter 失败，确认业务不会无限等待，且遥测丢失有独立信号。

### GenAI 约定仍有版本边界

2026-11-17 读取的官方旧路径已指向 `open-telemetry/semantic-conventions-genai` 独立仓库。本轮固定 commit `e6658f14c9d9ea0760825f029cb82e7673f48fab` 的 client span 文档标为 **Development**。所以应记录 instrumentation 包版本、语义映射版本和后端字段映射；不能把不同 SDK 的 `gen_ai.system` 与 `gen_ai.provider.name` 不加说明地混在同一看板。

这份合同建议一个 span 覆盖一次逻辑操作，包括 SDK 自动重试；应用若另外记录每次网络 attempt，应明确父子关系和 `attempt` 字段，避免把父 span 与子 attempt 的同一 usage 重复相加。流式调用要到流结束、取消或失败才结束 span，不能收到第一个 chunk 就报成功。

内容字段如输入消息、输出消息及系统指令是 opt-in。默认先收集操作类型、模型标识、时延、用量、状态、引用数量和经过审核的错误分类；确需正文时，设置采样、脱敏、访问权限与保留期。异常 message、HTTP header 和工具返回也可能含凭据，只关掉 prompt capture 并不够。

### 实例一：RAG 回答质量下降，但 HTTP 全成功

一个请求 trace 依次包含权限过滤、检索、重排、生成和引用校验。分别记录候选数量、授权后数量、资料版本、最终引用与校验结果，但不默认存整段客户文档。模型正常返回而引用不属于检索集合时，技术调用可以成功，业务结果仍为失败。

排障按最便宜证据推进：先比发布前后的检索配置与资料版本，再查空检索率、截断和过滤变化，最后才调整模型。不要把“模型比较弱”当第一个解释。LLM-as-Judge 的分数需要评审器版本、样本选择与人工校准；错误样本过采样能找问题，却不能直接代表全体请求失败率。

### 实例二：工具写入超时与审批等待

将活动执行时长、用户等待时长和整个业务单存续时间分开；数小时审批不应被算成模型延迟。恢复后的请求可有新的 trace，通过业务 operation ID 或 span link 关联，不要求一个网络请求保持到审批结束。

外部写入超时记为 `unknown` 而不是已失败；随后用业务幂等键回查真实对象。回查确认成功才记 `verified_success`，确认未执行才考虑重试。追踪记录应包含请求摘要、审批记录引用、幂等键引用、回执和回读时间，但敏感 ID 不用作 metrics label。按端点/操作/结果等低基数维度聚合，避免把每个用户或订单都变成时序标签。

## 六、本地可执行的用量与完成率口径

下面是标准库参考实现，**不调用模型或遥测平台**。输入是明确构造的教学数据，不是生产观测。`normalize_usage` 假定适配器已经转换为“输入总量包含缓存命中”的口径；不满足此口径的供应商必须先单独适配，不能直接套用。缺失 usage 表示未知，不补零；缓存输入不得大于输入总量；输出不额外叠加已被 provider 计入其中的 reasoning token。

```python
# kb-test: telemetry-accounting
from decimal import Decimal
from collections import Counter

def normalize_usage(raw: dict):
    fields = ("input_tokens", "output_tokens", "cached_input_tokens")
    if any(raw.get(k) is None for k in fields):
        return None
    if any(type(raw[k]) is not int or raw[k] < 0 for k in fields):
        raise ValueError("token counts must be non-negative integers")
    i, o, c = (raw[k] for k in fields)
    if c > i:
        raise ValueError("cached input exceeds total input")
    return {"uncached_input": i - c, "cached_input": c, "output": o}

def token_cost(usage, rates: dict):
    # rates: 每百万Token的同币种价格；不含缓存写入、工具与存储费用。
    if usage is None:
        return None
    total = Decimal("0")
    for key in ("uncached_input", "cached_input", "output"):
        if type(usage[key]) is not int or usage[key] < 0:
            raise ValueError("invalid normalized usage")
        rate = Decimal(str(rates[key]))
        if not rate.is_finite() or rate < 0:
            raise ValueError("invalid rate")
        total += Decimal(usage[key]) * rate
    return total / Decimal(1_000_000)

def completion_summary(outcomes: list[str]):
    allowed = {"verified_success", "failed", "unknown", "cancelled"}
    if any(x not in allowed for x in outcomes):
        raise ValueError("unknown outcome label")
    counts = Counter(outcomes)
    n = len(outcomes)
    return {"requests": n, "verified_success": counts["verified_success"],
            "unknown": counts["unknown"],
            "verified_rate": counts["verified_success"] / n if n else None}
```

成本账本还应保存币种、价格生效时间、provider、请求模型/响应模型以及价格来源。上述函数只是三类 Token 的计价器，不是完整账单：缓存写入、长上下文阶梯、批量折扣、工具或搜索计费需按服务合同扩展，缺字段时保持未知。采样 trace 的成本合计也不能冒充全量账单，费用应优先对齐完整 usage 事件与供应商账单。

完成率按**业务请求**计数，不按模型轮次或工具次数计数。示例规定 unknown/cancelled 仍进入分母，便于暴露未完成业务；团队可以另定义“可服务请求成功率”，但必须单列排除项与分母。空集合返回未知而非 100%。一条请求的重试最终成功只算一次成功，各次真实计费调用则都要计费。
