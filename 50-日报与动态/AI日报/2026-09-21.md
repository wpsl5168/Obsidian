## 一、Qwen-Image-2.1：先看商用许可，再看“7B”

[官方正文](https://qwen.ai/blog?id=qwen-image-2.1) · [HN 49775499](https://news.ycombinator.com/item?id=49775499) · [代码与README](https://github.com/QwenLM/Qwen-Image-2.1) · [权重及模型卡](https://huggingface.co/Qwen/Qwen-Image-2.1) · [实际许可](https://huggingface.co/Qwen/Qwen-Image-2.1/blob/main/LICENSE)

发现入口为允许的HN，原帖在北京时间9月20日21:09:25提交，本轮674分；文章和仓库News均标9月20日。按本窗口新讨论收录，不改写成9月21日首发。Qwen不在本任务五家官方发现源名单内，本条是由合格HN条目回核其原始发布材料。

Qwen-Image-2.1将文生图、图像编辑与透明RGBA输出合入同一模型，最多接收10张参考图。可以生成透明素材、编辑透明层、从RGB照片提取透明主体，局部编辑支持涂圈、涂抹或另给mask。以上是作者文档与展示声明，本轮未运行模型、未分析示例图以验证效果。

架构要拆开看：7B指32层Single-Stream DiT视觉生成模块；README另列Qwen3-VL 8B文本/视觉编码器和64通道RGBA VAE。不能把“7B”当整条推理管线总参数或显存承诺。混合粒度attention让文本使用token级因果mask、图像使用chunk级mask；条件图和指令作为静态前缀在首个去噪步骤计算，再复用KV cache。文档默认40步、2048×2048，并提供CPU offload；本轮没有独立速度、显存或画质实测。

权重不是只有一个公告链接：HF API文件列表可见text_encoder四份safetensors、transformer两份、VAE一份，模型状态非gated；本轮只核文件目录，没有下载大权重或运行。README推荐从Git安装Diffusers、transformers≥5.17，也推荐另用Qwen3.5-VL 9B提示词改写模型，不能把可选改写器算进基础生成性能却不交代。

商业边界比发布文案更重要。GitHub实际LICENSE与HF权重仓LICENSE逐字相同，均为Qwen Research License Agreement，发布日期9月20日；非商业限定为研究或评估，商用必须另行取得授权，联系地址为model-business@notice.qwencloud.com。HF模型卡标license: other / qwen-research，GitHub API标Other。虽然博客使用“open-source”，本报不将其写成Apache/MIT式可直接商用开源。

## 二、Kev：准确率上升，不代表可以少设人工兜底

[项目](https://github.com/jaredpalmer/kev) · [release](https://github.com/jaredpalmer/kev/releases/tag/kev-family) · [9B模型卡](https://github.com/jaredpalmer/kev/blob/main/docs/model-cards/kev-9b.md) · [HN 49783999](https://news.ycombinator.com/item?id=49783999)

HN北京时间9月21日15:11:55提交，本轮183分。`kev-family`正式release发布于9月21日01:18:57 CST，非draft、非prerelease；release及README明确另标“2026-09-21 update”。仓库创建于9月18日04:49:39 CST，不是本窗才创建。

Jared Palmer的Kev基于Qwen3.5提供0.8B、4B、9B三种决策模型。每个checkpoint是冻结Qwen基础模型上的rank-16 LoRA适配器及pointer head，输入共享文本和类型化问题，输出yes/no、choice、score概率，不进行自回归文本生成。Qwen3.5的Gated DeltaNet层不遵守attention mask，因此实现中将各问题放到独立行，共享state缓存；“问题隔离”不等于同一问题的选项顺序不影响答案。

本轮实质更新是短程二次训练：加入显式天数的日期政策题，以及去掉决定性证据、目标为均匀分布的样本。作者报告9B在域外locked test准确率由0.837变为0.852，4B由0.832变为0.837，0.8B由0.668变为0.684。数据均为项目方自测，未经本轮复现。9B模型卡同时承认代价：域外开发集在≤5%错误预算下可自动处理的覆盖率由0.53降到0.47，原始概率≥0.9但答错的占比由7.5%升到8.7%。不能把准确率改善等同于更安全的自动决策。

比较口径：Kev-9B域外开发集0.822，Jev同一开发集0.857；Kev的0.852是另一个locked test，Jev没有该test结果，不能用0.852对比0.857宣称几乎追平。作者不知道Jev训练数据，也明确不是架构间严格控制实验。release与模型卡对0.837→0.852另写“+1.8 pp”，与展示端点的简单差不一致，本稿仅引用端点，不照搬增量或置信区间；README与模型卡关于unknowable及个别外部测试也存在版本口径差异，未选这些数字。

可选校准参数`KEV_TEMPERATURE=2.0`只调整概率、不改变argmax答案；作者报告域外开发集ECE由0.106到0.050，高置信错误8.7%到4.4%。`KEV_DATE_FACTS=1`则是外部日期预处理，把绝对日期差补进state，不能把其收益归为模型自身算术能力。模型卡明确部分日期能力被LoRA训练削弱。

部署边界：README要求Python 3.12+，当前模型需transformers≥5.17；Mac上缺DeltaNet高效MPS kernel，作者M5/bf16、约230-token state、5问题各3选项测试中4B中位779ms（旧Qwen3 4B为174ms），9B约2秒。默认仅绑定127.0.0.1且无鉴权，一次处理一个请求；首次启动下载适配器和基础模型。所核仓库LICENSE为Apache-2.0；模型卡声明adapter/head及基础模型Apache-2.0，训练数据各自许可，未逐个审数据集。

原文摘录：
> The server binds to `127.0.0.1` and has no authentication.

> We don't know which datasets Jev was trained on, so this isn't a controlled comparison of the two architectures.

> What the delta cost. Coverage at ≤ 5% error fell ... confident errors rose ...

工程判断：决策模型值得试的是固定标签输出与可校准概率，不是“没有自由文本就没有错误”。上线审批、路由等流程，应看业务数据上的错误预算和覆盖率，不能只看准确率榜单。

## 四、Simon Willison：把密钥输入从Agent会话中拿出去

原文：https://simonwillison.net/2026/Sep/20/llm-keys-ui/

作者仓库固定版本：https://github.com/simonw/llm-keys-ui/tree/0.1

正式发布：https://github.com/simonw/llm-keys-ui/releases/tag/0.1

### 已核事实

Simon介绍了LLM插件llm-keys-ui 0.1。使用Codex Remote从手机操作远程机器时，他不想把API密钥直接粘进ChatGPT或Agent会话，因此做了一个写入LLM密钥存储的Web表单。Agent可以启动界面、返回机器地址，用户再通过浏览器录入密钥。正文明确说，后续Agent仍可通过`llm keys get anthropic`等shell命令使用密钥。

正文标“20th September 2026”，页尾显示7:22 pm；Atom为`2026-09-20T19:22:19+00:00`。GitHub正式release的`published_at`同为`2026-09-20T19:22:19Z`，即北京时间9月21日03:22:19，在主窗口内；非draft、非prerelease。9月20日归档及原Feed都没有该URL。

固定0.1版本README说明：默认监听`127.0.0.1:8010`；`--all`会改为监听`0.0.0.0`，打印所有本机IPv4地址的HTTP URL，供局域网或Tailscale访问。界面不实现身份认证，作者要求设置完密钥后停止服务；该界面不提供读取既有密钥值的功能。

只读检查0.1源码可核：文件存储在LLM用户目录的`keys.json`，以JSON写入，并将文件权限设为`0600`；有CSRF token校验及`no-store`等响应头。没有把这些保护描述成用户认证、加密保险库或完整安全审计。

原文引文：
> I don't like pasting API keys into agent sessions, so I wanted a way to get those keys onto a machine without pasting them into the ChatGPT app directly.

README引文：
> The interface does not implement authentication. Stop the server once you have set your keys.

> Existing key values cannot be read using this tool.

### 工程判断（本报推论，与事实分开）

可迁移的是“秘密通过独立输入通道进入执行环境，而非进入聊天上下文”的做法，不是“Agent从此无法读取密钥”。作者明确允许shell取钥；拥有相同文件权限或shell权限的Agent仍能访问密钥，秘密也可能因后续命令输出进入日志。

不宜把文章里的`--all`直接当成安全默认值：它扩大监听范围，应用又没有认证。实际使用应优先loopback配受控隧道，或以网络访问控制限制可达者，录入后立即关闭。CSRF保护针对跨站请求，不替代访问者身份认证；不显示旧值也不阻止可达者修改密钥。本轮没有安装运行、端口暴露或渗透测试，以上是基于固定版本README和代码的边界判断。

[作者原文](https://www.buchodi.com/chatgpt-now-knows-what-you-do-on-other-websites-via-ad-collector/) · [HN 49776729](https://news.ycombinator.com/item?id=49776729)

作者Jamie Larson称在Android Chrome抓包，观察到ChatGPT签发绑定账号subject与`obi`的token，collector设置`.openai.com`下`__obi` cookie，SameSite=None、Secure、HttpOnly、有效期一年；其后广告主网站加载OpenAI pixel/SDK时，请求携带该cookie。作者称个人设备在12商业网站、13 pixel ID上观察到此行为；更大流量样本覆盖936 advertiser pixels、1,029 hostnames。

不能照抄HN标题“ChatGPT已经知道你在其他网站做什么”：作者明确没有观察服务端实际join到账号，HTTP 202仅表示collector接受事件。也未证明数据进入ChatGPT回答、训练或任意浏览历史；仅是安装相应广告标签的网站。浏览器范围限Android Chrome，桌面Chrome未测，作者称iOS因第三方cookie限制不发生；约五分之一ChatGPT session产生sync token，不能推广至全部用户。

作者称9月14日向OpenAI询问analytics而非marketing同意的分类，仅收到Support确认转内部，未回答问题。本轮未独立抓包、未打开官方cookie政策核当前原文，官方回应与cookie分类仅按作者转述，不写成OpenAI承认违规。本条可作署名研究报道，若主编要求一手官方双核则暂留候选。
