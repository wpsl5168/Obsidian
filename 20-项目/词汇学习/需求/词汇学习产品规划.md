# 词汇学习产品规划 · Lexi(暂名)

> 2026-07-28 · 老王 × 小虾
> 定位：知识库驱动 + AI 辅助的个人词汇学习系统
> 前身：轻译 LightTranslate(WPF 词典)+ Basic English 训练器(Web SRS)

---

## 一、这不是拼接,是什么

两个现成应用摆在一起,最容易做的是加个 tab 把功能并列。那样做出来的东西没有护城河 —— 市面上词典 + 背单词的组合到处都是(欧路、扇贝、Anki)。

**真正的产品定义应该来自一个别人做不到的事实：**

> 你查过的每一个词,都是你真实知识边界的一次采样。

多邻国给你它的词表。扇贝给你四六级词表。**没有任何产品把「你自己遇到的词」当作第一手资产来经营。**

所以产品的核心不是"查词"也不是"背词",而是：

**把个人查询行为沉淀成一个可检索、可复习、可生长的私人词汇知识库,AI 在其上做个性化的理解与练习生成。**

三句话说清定位：

| 维度 | 定义 |
|---|---|
| 是什么 | 个人英语词汇知识库 |
| 输入 | 你在真实场景中查的每一个词/句 |
| 输出 | 按你的遗忘曲线和真实语境生成的练习 |

差异点不在功能清单,在**数据主权 + 语境真实性**：练习题里的例句,来自你自己看过的文档。

## 二、功能范围(四层)

### L0 · 采集层 —— 查词即入库

一切的起点。用户感知是"查词",系统行为是"采样"。

| 功能 | 说明 | 优先级 |
|---|---|---|
| 中英互译 | 词/句双向,自动识别方向 | P0(已有) |
| 词典查词 | 音标、分词性释义、例句、近反义词 | P0(已有) |
| 划词/热键取词 | PC 端全局热键,手机端分享菜单 | P0 |
| **来源标记** | 记录这个词在哪查的(URL/应用/手动备注) | **P0 新增·关键** |
| 整句翻译 | 双语对照 + 拼音 | P1(已有) |
| 剪贴板监听 | 复制即候选查询 | P2 |
| OCR 取词 | 截图/拍照识别 | P3 |

**「来源标记」是整个产品的地基。** 没有它,词就只是词;有了它,词带着语境,后面的 AI 出题和知识图谱才有原料。

### L1 · 知识库层 —— 词条不是记录,是笔记

这一层是和竞品的分水岭。传统单词本是 `word → 释义` 的平表。这里要做成**可生长的笔记**。

| 功能 | 说明 | 优先级 |
|---|---|---|
| 词条详情页 | 一个词一页,聚合所有查询历史、语境、笔记 | P0 |
| 自动打标 | 按来源域名/主题自动分类(技术/新闻/游戏) | P1 |
| 手写笔记 | 自己的助记、辨析、吐槽 | P1 |
| **语义相关词** | 基于 embedding 找出你库里语义相近的词 | **P1 差异点** |
| 词族聚合 | 同词根/同短语动词自动归组 | P2 |
| 词书导入 | 中考/四六级/雅思等标准词表,与个人库并存 | P2 |
| 双链引用 | 词条之间 `[[]]` 互链,像 Obsidian | P3 |

**语义相关词**是老王已有基建能直接吃到的红利 —— OpenHippo 现成 24458 条向量的 embedding 管道,同样的 nomic/openai embedding 可以直接给词条用。这个能力扇贝、欧路都没有。

### L2 · 学习层 —— AI 生成的个性化练习

现有训练器的 Leitner 引擎(`0/1/3/7/15/30` 天,5 级盒子)是合格的骨架,直接复用。要换掉的是**题目的来源**。

| 功能 | 说明 | 优先级 |
|---|---|---|
| SRS 调度 | Leitner 5 级,到期队列 | P0(已有) |
| 认 · Recognize | 英→中选择 | P0(已有) |
| 用 · Produce | 中→英拼写/组合 | P0(已有) |
| 造 · Output | 造句 + 对照 | P0(已有) |
| **AI 出题** | 用你的真实语境句挖空,而非通用例句 | **P0 差异点** |
| **AI 批改** | 造句题给出语法/地道度反馈,而非只对照标准答案 | **P1 差异点** |
| 听力题 | TTS 读音 → 拼写 | P1 |
| 每日任务 | 到期词 + 新词,固定 10-15 题 | P0(已有) |
| 弱项报告 | 哪些词反复错、哪类词性薄弱 | P2 |

**AI 出题的具体形态**(这是产品的记忆点)：

> 你三周前在读 Azure 文档时查过 `throttling`。
> 今天复习到它,题目是把当时那句原文挖空让你填,而不是词典里的通用例句。

情境重现的记忆效果远高于孤立例句 —— 这是认知心理学的 encoding specificity,也是这个产品最值得吹的一句话。

### L3 · 洞察层 —— 让人愿意每天打开

| 功能 | 说明 | 优先级 |
|---|---|---|
| 进度激励 | XP / streak / 掌握计数 | P0(已有) |
| 词汇量估算 | 基于已掌握词推算总词汇量 | P2 |
| 领域雷达 | 你的词汇分布在哪些领域,哪块弱 | P2 |
| 时间轴 | 这个月新增/掌握了哪些词 | P2 |
| 周报 | 邮件/微信推送本周学习摘要 | P3(可挂 cron) |

## 三、形态选型 —— 三个候选

约束条件：
- 必须多端(手机 + PC),手机是背单词主场景,PC 是查词主场景
- 老王强偏好：不改 Hermes 源码,基建尽量复用
- VM 现状：8GB 内存已用 3.1G,磁盘 61G 用 76%,禁重服务
- 现有资产：WPF 桌面端(C#)、静态 Web 训练器、Caddy 反代、OpenHippo

### 候选 A · PWA 单体(前端 + 轻 API)

一个 Web 应用打天下,手机加桌面图标当 App 用,PC 浏览器直接开。

| 维度 | 评价 |
|---|---|
| 工期 | 中(3-4 周到 MVP) |
| 多端 | ✅ 天然全平台,一套代码 |
| 离线 | ✅ Service Worker + IndexedDB |
| PC 划词 | ❌ **浏览器无法全局取词** |
| 复用现有 | 训练器 100% 复用;**WPF 投入基本作废** |
| 运维 | 轻,Caddy 加一个站点 |

### 候选 B · 本地优先 + 同步服务(推荐)

Web 端(PWA)是主战场,WPF 桌面端降级为「取词客户端 + 本地词典」,两端通过一个极薄的同步 API 交换数据。

| 维度 | 评价 |
|---|---|
| 工期 | 中偏长(4-6 周,但可分期见效) |
| 多端 | ✅ Web 全平台 + PC 原生取词 |
| 离线 | ✅ 两端都本地优先 |
| PC 划词 | ✅ WPF 保留全局热键 |
| 复用现有 | ✅ **两边资产全保** |
| 运维 | 中,多一个同步服务 |

关键设计：**Web 是数据权威,桌面是采集探针。** 桌面只做两件事 —— 取词、把结果 push 到云端。所有复习、知识库、AI 都在 Web。这样桌面端代码量不增反减,维护成本可控。

### 候选 C · 全栈 Next.js + 浏览器扩展

放弃 WPF,PC 端取词改用浏览器扩展(Chrome/Edge)。

| 维度 | 评价 |
|---|---|
| 工期 | 长(6-8 周,扩展要过审) |
| 多端 | ✅ 全平台 |
| PC 划词 | ⚠️ 仅浏览器内,PDF/Word/终端取不到 |
| 复用现有 | WPF 作废 |
| 运维 | 重(Next.js SSR 常驻,VM 内存吃紧) |
| 额外收益 | 扩展有分发渠道,是唯一有增长可能的路线 |

### 决策

**选 B。** 理由三条：

1. **场景真实性**：老王 PC 上查词大量发生在 Azure 文档、PDF、终端 —— 浏览器扩展覆盖不到,WPF 全局热键能。这个能力值钱,别扔。
2. **资产保全**：两个项目都不白做。C# 那部分砍成薄客户端后维护量很小。
3. **风险可控**：Web 端独立可用,桌面端挂了不影响主流程。反过来也成立。

放弃 C 的关键理由：Next.js SSR 常驻进程在这台已经跑着 Hermes + OpenHippo + ollama + 5 个容器的 8G VM 上,是明确的内存风险。**PWA 静态化 + 极薄 API 才是这台机器的正确姿势。**

## 四、技术架构

```
┌──────────────────┐         ┌──────────────────┐
│  WPF 桌面探针     │         │   PWA (手机/PC)   │
│  ─────────────   │         │  ──────────────  │
│  全局热键取词      │         │  查词 / 知识库     │
│  本地词典缓存      │         │  SRS 复习         │
│  离线队列         │         │  AI 练习          │
└────────┬─────────┘         └────────┬─────────┘
         │  POST /lookup             │  IndexedDB
         │  (词 + 语境 + 时间)         │  (本地优先)
         └───────────┬───────────────┘
                     ▼
         ┌───────────────────────────┐
         │   Sync API (FastAPI 单进程) │
         │   ─────────────────────    │
         │   /sync   增量拉取/推送      │
         │   /embed  词条向量化         │
         │   /ai     出题 / 批改        │
         └───────────┬───────────────┘
                     ▼
         ┌───────────────────────────┐
         │  SQLite + sqlite-vec       │
         │  (词条 / 语境 / SRS / 向量)  │
         └───────────────────────────┘
```

### 选型说明

| 层 | 选择 | 理由 |
|---|---|---|
| 前端 | 原生 JS + PWA,不上框架 | 现有训练器就是原生的,428 行跑得很好;上 React 是给自己找编译链 |
| 存储(端) | IndexedDB | 离线优先,容量够 |
| 后端 | FastAPI 单进程 | OpenHippo 就是这套,老王熟;内存占用小 |
| 存储(云) | SQLite + sqlite-vec | 单文件,好备份;向量能力现成(OpenHippo 已验证) |
| Embedding | 复用 ollama nomic(768维) | 已跑着,零新增内存 |
| AI 出题 | Copilot 网关 / OpenAI 兼容 | 桌面端已实现 OpenAI 兼容调用,直接复用 |
| 同步策略 | 时间戳 last-write-wins | CRDT 是过度设计,单用户场景不会真冲突 |
| 部署 | Caddy 加站点 + systemd 一个服务 | 与现有基建同构 |

### 关键约束(踩过的坑)

- **CORS**：`translate.googleapis.com` 在浏览器会被挡。Web 端翻译必须走自己的 API 代理,不能直连。
- **embedding 同源性**：换 embedding 后端必须全量重嵌,nomic 和 openai 的向量空间不能混存(OpenHippo 已经踩过)。
- **内存预算**：新增服务必须控制在 300MB 以内。FastAPI + SQLite 可以做到。

## 五、界面形态

### 信息架构(四个 Tab)

| Tab | 名称 | 核心动作 |
|---|---|---|
| 1 | 查 | 输入框 + 结果卡片,秒开秒查 |
| 2 | 库 | 词条列表 / 搜索 / 标签筛选 |
| 3 | 练 | 今日任务,进入即答题 |
| 4 | 我 | 统计 / 设置 / 同步状态 |

### 三个关键界面

**查词页** —— 极简,顶部输入框常驻焦点。结果卡片纵向流：词头+音标+发音 → 分词性释义 → 例句 → **AI 解读(折叠,点开才请求)** → 底部一排动作(加入词库 / 收藏 / 跳转专业源)。

**词条详情页(新增,产品灵魂)** —— 这页决定产品是"工具"还是"知识库"：
- 顶部：词头、音标、掌握度进度条
- 释义区：标准词典释义
- **我的语境**：这个词你查过几次、每次在哪、原句是什么(带时间轴)
- **我的笔记**：自由文本
- **语义相关**：库里语义相近的词(embedding 召回)
- 底部：SRS 状态、下次复习时间

**练习页** —— 沿用现有训练器的视觉(奶油底/墨绿主/琥珀点缀,已经很好看,别动)。变化在题目内容：题干上方多一行小字标注来源 `来自你 7 月 3 日读的 Azure 文档`。

### 视觉方向

现有训练器的配色是 editorial 风格(暖纸底 `#f4f1e9` / 墨绿 `#2f6b4f` / 琥珀 `#c98a2b`),配 Playfair Display 衬线标题。**这套视觉直接定为产品设计语言**,WPF 端也往这个方向靠。理由：已经做得好,且和市面上蓝紫渐变的学习 App 拉开距离,符合"知识库"而非"游戏"的定位。

## 六、分期路线

| 期 | 目标 | 交付 | 工期 |
|---|---|---|---|
| **P0** | 数据地基 | 统一 schema(词条/语境/SRS);SQLite 建库;两端读写打通 | 3-5 天 |
| **P1** | Web 端可用 | PWA:查词 + 词库 + 复习三件套,IndexedDB 离线 | 1-2 周 |
| **P2** | 桌面端降级 | WPF 砍成取词探针,查词结果 push 到云 | 3-5 天 |
| **P3** | AI 层 | 语境挖空出题 + 造句批改 | 1 周 |
| **P4** | 知识库层 | 词条详情页 + 语义相关词(embedding) | 1 周 |
| **P5** | 洞察层 | 统计 / 领域雷达 / 周报 cron | 3-5 天 |

**MVP 定义 = P0 + P1 + P2。** 到这一步,产品就已经是"多端可用的个人词汇库",可以自己每天用了。P3 之后是差异化增强。

## 七、风险

| 风险 | 影响 | 对策 |
|---|---|---|
| VM 内存吃紧(已用 3.1G/7.8G) | 新服务可能触发 OOM | FastAPI 单进程 + SQLite,控制在 300MB;上线前跑压测 |
| 磁盘 76% | 向量库增长 | 词条量级远小于 OpenHippo,预估 <100MB |
| 免费词典 API 限流 | 查词失败 | 本地缓存 + 多源降级(dictionaryapi → wiktionary → AI) |
| AI 出题成本 | 每题一次 LLM 调用 | 批量生成 + 缓存,一个词的题目生成一次复用多轮 |
| 独自开发,战线长 | 做一半烂尾 | 严格按 P0→P1→P2 走,每期都是可用状态 |
| 数据丢失 | 词库是核心资产 | SQLite 每日备份进 Obsidian 的 git |

## 八、命名候选

| 名字 | 释义 | 评价 |
|---|---|---|
| **轻译 Lexi** | 沿用"轻译"品牌 + Lexicon | 延续性好,但"译"字偏工具 |
| **词库 / Wordbase** | 直白 | 太平,没记忆点 |
| **语境 / Contexta** | 直击差异点 | 中文名有点绕 |
| **拾词 / Pickup** | 捡拾遇到的词 | 有画面感,契合"采样"定位 |

倾向 **拾词**：动作感强,准确描述了产品行为(把你路上遇到的词捡起来),且和"背单词"这个苦役感的词拉开距离。
